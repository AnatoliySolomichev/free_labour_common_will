# Типы записей блокчейна

**Статус:** черновик v0.2
**Основание:** обсуждение семантического слоя, апрель 2026.
**Назначение:** описание структуры данных, хранимых в поле `payload` пользовательских блоков. Является надстройкой над транспортным слоем, описанным в `blockchain.md`.

---

## 1. Назначение

Поле `payload` блока типа `DATA` содержит произвольные байты в формате CBOR. Данный документ определяет стандартные типы записей — семантический слой, на котором строится граф знаний, трудовая экономика и производственные цепочки.

Ключевой принцип: **запись идентифицируется своим содержимым**. Хеш записи (BLAKE2b-256 от её CBOR-представления) является её адресом. Ссылки между записями — контентно-адресованные.

---

## 2. Формат записи

Каждая запись — CBOR-map с обязательным полем `"t"` (тип, `uint8_t`) в качестве первого ключа (по правилам deterministic CBOR ключи сортируются по длине затем лексикографически; `"t"` — 1 байт, сортируется раньше более длинных ключей).

```
Record = CBOR map {
  "t": uint8_t,   // дискриминатор типа (см. таблицу records.md §3)
  ...             // поля, специфичные для типа
}
```

Один блок содержит одну запись или упорядоченный список записей:

```
Block.payload = CBOR encode(Record)
             | CBOR encode([Record, Record, ...])
```

## 3. Дискриминаторы типов

| Диапазон | Категория |
|----------|-----------|
| 0x00–0x0F | Базовые / структурные |
| 0x10–0x1F | Онтологические примитивы |
| 0x20–0x2F | Модификаторы |
| 0x30–0x3F | Программные примитивы |
| 0x40–0x4F | Граф знаний |
| 0x50–0x5F | Трудовые записи |
| 0x60–0x6F | Производство |
| 0x70–0x7F | Экономика |
| 0x80–0xFF | Зарезервировано |

## 3A. Структурные / протокольные записи (0x00–0x0F)

Записи, относящиеся к протоколу блокчейна (`blockchain.md`), а не к семантике знаний/экономики. В отличие от базовых примитивов (blockchain.md §4), имеют собственный дискриминатор.

### 3A.1. FraudClaim (0x01) — Обвинение в структурном обмане

Обвинение merge-блока (blockchain.md §6.5) в криптографически невалидном содержимом снимка. Пишется в блокчейн **обвинителя**, ссылается на обвиняемый блок через `Ref` (в чужую цепь писать нельзя). Само обвинение веса не имеет — вес даёт **приложенное самопроверяемое доказательство**; агрегатор/читатель верифицирует его прежде, чем учесть. Это негативный двойник со-подписи слияния (blockchain.md §6.5.5): со-подпись = «ручаюсь, что честно», `FraudClaim` = «доказываю, что нет».

**Область действия.** Ловит только **структурный/криптографический** обман. Sybil (валидные, но фальшивые личности) `FraudClaim` не ловит — это задача репутационного слоя (граф экономического обмена, blockchain.md §6.5.4).

```
FraudClaim = {
  "t":      0x01,
  "target": Ref,          // обвиняемый merge-блок {chain, hash}
  "kind":   Text,         // "bad_sig" | "hash_mismatch"
  "proof":  Map,          // доказательство, зависит от kind
  "reason": Text?         // человекочитаемое пояснение (опционально)
}
```

Поддерживаются только **позитивно доказуемые** виды. Доказательство отсутствия («блока нет вообще», «count завышен») в открытой сети недоказуемо и в блокчейн не выносится — остаётся локальным игнором.

Оба вида несут общий набор полей (blockchain.md §6.5.6): помимо листа и пути Меркла, обязателен **путь узлов** участника — без него нельзя добраться до `working_pubkey` и проверить подпись блока (см. blockchain.md §6.5.5, проблема отсутствия ключа).

```
proof = {
  "leaf":      { "chain": Bytes(32), "node": Int, "block": Int, "hash": Bytes(32) },  // оспариваемый ExternalRef
  "merkle":    { "path": [Bytes(32), ...], "dirs": [Bool, ...] },  // включение H(leaf) в target.merkle_root
  "nodes":     [Node, ...],   // путь узлов root..node цепи chain → working_pubkey листового узла
  "evidence":  Block          // блок-улика (см. ниже, зависит от kind)
}
```

**kind = `"bad_sig"`** — `evidence` = сам блок-0 (его хеш = `leaf.hash`); проверяющий видит, что подпись блока **не проходит** по `working_pubkey`.

**kind = `"hash_mismatch"`** — `evidence` = настоящий подписанный блок участника по адресу `(chain, node, block)`; его подпись валидна, но хеш ≠ `leaf.hash` → зафиксированный хеш подделан.

**Проверка (любой вид):**

1. **Структура.** Пересчитать корень Меркла из `H(leaf)` и `merkle`, сверить с `target.merkle_root`; проверить путь узлов `nodes` (корень самоподписан и `= chain`, каждый узел подписан родителем, последний = `leaf.node`). Любой провал → доказательство **сфабриковано**. Из последнего узла берётся `working_pubkey`.
2. **Дефект.** `bad_sig`: `evidence` — тот же блок (`hash = leaf.hash`) и его подпись невалидна по `working_pubkey`. `hash_mismatch`: `evidence` по тому же адресу, подпись валидна, а хеш ≠ `leaf.hash`.

**Исход и вес:**

| Исход                   | Условие                                          | Вес                               |
|-------------------------|--------------------------------------------------|-----------------------------------|
| CONFIRMED               | п.1 и п.2 сошлись                                | сильный минус обвиняемому         |
| REFUTED (добросовестно) | путь сходится к корню, но дефект ложный          | ноль; штрафа обвинителю нет       |
| REFUTED (фабрикация)    | путь **не** восстанавливает `target.merkle_root` | ноль + штраф репутации обвинителю |

Штраф обвинителю — **только** за фабрикацию (провал п.1): это провабельно злонамеренно. Ошибка в дефекте при верном пути (п.1 прошёл, п.2 нет) штрафом не наказывается — обвинитель ткнул в реальный лист, но добросовестно ошибся.

**Проверка vs построение.** Само поле `proof` — непрозрачный blob (сериализованный `FraudProofData` транспортного слоя); `records` его не интерпретирует. *Проверка* реализована и самодостаточна: `blockchain::FraudProof::verify(kind, proof, merkle_root_of(target))` (CLI: `bc fraud verify`). *Построение* же требует сырого набора листьев обвиняемого пакета, путей узлов и блоков-улик — данных кеш/gossip-слоя, отложенных до модуля синхронизации (blockchain.md §6.5.6, blockchain.md §11.9).

## 4. Базовые типы (примитивы данных)

Используются как значения полей в других записях. Самостоятельного дискриминатора не имеют — это нативные типы CBOR.

| Тип | CBOR | Описание |
|-----|------|----------|
| `Null` | `0xf6` | отсутствие значения |
| `Bool` | `true`/`false` | логическое значение |
| `Int` | int / uint | целое (до 64 бит) |
| `Float` | float64 | вещественное |
| `Text` | text string | UTF-8, NFC-нормализация обязательна |
| `Bytes` | byte string | сырые байты |
| `List` | array | упорядоченная последовательность |
| `Map` | map | именованные поля {key: value} |

### Ссылка (Ref)

Ссылка на запись в любом блокчейне — основной механизм связей между записями и пользователями.

```
Ref = {
  "chain": Bytes(32),   // UserId: публичный ключ корневого узла владельца
  "hash":  Bytes(32)    // BLAKE2b-256 от CBOR-сериализации referenced блока
}
```

Верификация ссылки: загрузить блок с данным `hash` от пользователя `chain`, проверить совпадение хеша. Возможна как P2P (напрямую к владельцу), так и через агрегатор (см. records.md §13).

### BlockPath (встроенный)

Полный путь к блоку — та же форма, что `ExternalRef` слоя блокчейна (лист доказательства слияния выше): чья цепь, какая ветка двоичного дерева, какое место в ветке, и хеш содержимого для проверки.

```
BlockPath = {
  "chain": Bytes(32),   // UserId: публичный ключ корневого узла владельца
  "node":  Int,         // heap-индекс листового узла — ветка
  "block": Int,         // номер блока в этой ветке
  "hash":  Bytes(32)    // BLAKE2b-256 блока — контроль
}
```

**Зачем и путь, и хеш.** По протоколу в ветке не может быть двух блоков с одним индексом (`blockchain.md §9.5`), поэтому для **действительной** цепи адрес однозначен сам по себе — и по нему до блока можно дойти руками, без всякого индекса. Но украденный ключ или владелец, раздвоивший свою ветку, могут **подписать** второй блок на том же адресе (`blockchain.md §6.7`) — недействительный, улику форка, но существующий. Хеш говорит, какой из них имелся в виду, и доказывает, что блок с тех пор не переподписан.

Используется там, где по ссылке нужно уметь пройти самому: ось в разбивке цены (`records.md §9.5` v4).

### Quantity (встроенный)

Используется как значение поля, не как самостоятельная запись.

```
Quantity = { "v": Float, "u": Text }   // v: значение, u: единица ("час", "кг", "м³", ...)
```

## 5. Онтологические примитивы (0x10–0x1F)

Базовые категории для описания реальности. Из этих примитивов строятся все остальные типы.

### 5.1. Entity (0x10) — Сущность

Поименованная вещь или субъект.

```
Entity = {
  "t":    0x10,
  "name": Text,
  "desc": Text?,
  "attr": Map?           // произвольные атрибуты {key: value}
}
```

### 5.2. Process (0x11) — Процесс

Изменение во времени.

```
Process = {
  "t":    0x11,
  "name": Text,
  "desc": Text?
}
```

### 5.3. State (0x12) — Состояние

Снимок сущности в момент времени.

```
State = {
  "t":      0x12,
  "entity": Ref | Text,
  "value":  any,
  "at":     Int?          // Unix timestamp (опционально)
}
```

### 5.4. Event (0x13) — Событие

Процесс в конкретный момент и место.

```
Event = {
  "t":       0x13,
  "process": Ref | Text,
  "agent":   Ref?,
  "at":      Int?,
  "loc":     Ref | Text?,
  "inputs":  [Ref | Quantity]?,
  "outputs": [Ref | Quantity]?
}
```

### 5.5. Property (0x14) — Свойство

Характеристика сущности.

```
Property = {
  "t":     0x14,
  "name":  Text,
  "value": any,
  "unit":  Text?
}
```

### 5.6. Relation (0x15) — Отношение

Направленная связь между двумя сущностями.

```
Relation = {
  "t":    0x15,
  "from": Ref,
  "to":   Ref,
  "kind": Text    // "является частью", "зависит от", "применяет", "порождает", ...
}
```

### 5.7. TimeRecord (0x16) — Время

```
TimeRecord = {
  "t":    0x16,
  "kind": "moment" | "period",
  "from": Int,             // Unix timestamp, UTC
  "to":   Int?             // только для "period"
}
```

### 5.8. Location (0x17) — Место

```
Location = {
  "t":    0x17,
  "name": Text?,
  "geo":  [Float, Float]?,  // [lat, lon]
  "ref":  Ref?              // ссылка на внешнюю запись места
}
```

### 5.9. Role (0x18) — Роль

Сущность в конкретном контексте (например: человек в роли электрика 3-го разряда).

```
Role = {
  "t":      0x18,
  "entity": Ref,            // ссылка на Worker или другую Entity
  "as":     Ref | Text,     // вольное описание роли или должность
  "in":     Ref?            // кооператив/организация (опционально)
}
```

## 6. Модификаторы (0x20–0x2F)

Изменяют смысл другой записи не создавая новую сущность.

### 6.1. Negation (0x20) — Отрицание

```
Negation = { "t": 0x20, "of": Ref }
```

### 6.2. Degree (0x21) — Степень

```
Degree = { "t": 0x21, "of": Ref, "k": Float }   // k: коэффициент 0.0–∞
```

### 6.3. ConditionMod (0x22) — Условный модификатор

Применяет запись только при выполнении условия.

```
ConditionMod = {
  "t":    0x22,
  "when": Ref,     // предикат (ссылка на запись-условие)
  "then": Ref      // применяемая запись
}
```

### 6.4. Approximation (0x23) — Приближение

```
Approximation = { "t": 0x23, "of": Ref, "from": any, "to": any }
```

### 6.5. TemporalMod (0x24) — Временной модификатор

```
TemporalMod = {
  "t":    0x24,
  "of":   Ref,
  "kind": "always" | "sometimes" | "during" | "never",
  "time": Ref?
}
```

### 6.6. CausalLink (0x25) — Причинно-следственная связь

```
CausalLink = {
  "t":      0x25,
  "cause":  Ref,
  "effect": Ref
}
```

## 7. Программные примитивы (0x30–0x3F)

Позволяют описывать алгоритмы и правила как данные (гомоиконичность). Используются для формализации правил расчёта коэффициентов, валидации записей и описания алгоритмов в базе знаний.

### 7.1. Variable (0x30)

```
Variable = { "t": 0x30, "name": Text, "type": Text? }
```

### 7.2. Binding (0x31)

```
Binding = { "t": 0x31, "var": Text, "val": any }
```

### 7.3. IfThen (0x32)

```
IfThen = {
  "t":    0x32,
  "cond": any,       // предикат
  "then": any,       // ветка «истина»
  "else": any?       // ветка «ложь» (опционально)
}
```

### 7.4. ForEach (0x33)

```
ForEach = {
  "t":    0x33,
  "var":  Text,
  "in":   Ref | List,
  "body": any
}
```

### 7.5. While (0x34)

```
While = {
  "t":    0x34,
  "cond": any,
  "body": any
}
```

### 7.6. Sequence (0x35)

```
Sequence = {
  "t":     0x35,
  "steps": [any, ...]
}
```

### 7.7. Function (0x36)

```
Function = {
  "t":      0x36,
  "name":   Text,
  "params": [Text, ...],    // имена параметров
  "body":   any
}
```

### 7.8. Apply (0x37)

```
Apply = {
  "t":    0x37,
  "fn":   Ref,
  "args": [any, ...]
}
```

### 7.9. BinaryOp (0x38)

```
BinaryOp = {
  "t":  0x38,
  "op": "+" | "-" | "*" | "/" | ">" | "<" | "=" | "!=" | "and" | "or",
  "l":  any,
  "r":  any
}
```

### 7.10. UnaryOp (0x39)

```
UnaryOp = {
  "t":  0x39,
  "op": "not" | "neg",
  "v":  any
}
```

**Пример — правило валидации приёмки:**

```
rule_accept = IfThen {
  cond: BinaryOp { op: "=", l: Variable "quality", r: "пройдено" },
  then: Apply { fn: Ref(fn_compute_labor_units), args: [Variable "hours", Variable "grade"] },
  else: Binding { var: "labor_units", val: 0 }
}
```

## 8. Граф знаний (0x40–0x4F)

### 8.1. Concept (0x40) — Идея / концепция

Атомарная единица знания.

```
Concept = {
  "t":    0x40,
  "text": Text,
  "tags": [Text, ...]?
}
```

### 8.2. ConceptLink (0x41) — Связь между концепциями

```
ConceptLink = {
  "t":    0x41,
  "from": Ref,
  "to":   Ref,
  "kind": Text    // "уточняет", "противоречит", "применяет", "порождает", ...
}
```

### 8.3. Composite (0x42) — Обобщающая идея

Группа связанных концепций, объединённых под общим заголовком.

```
Composite = {
  "t":     0x42,
  "title": Text,
  "parts": [Ref, ...]    // ссылки на Concept, ConceptLink, другие Composite
}
```

Хеш Composite является его идентификатором. Два Composite с одинаковым составом и порядком частей имеют одинаковый хеш — это их «тип» по содержанию.

**Открытый вопрос 14.3:** порядок в `parts` влияет на хеш. Нужно решить: сортировать ли ссылки (детерминированный хеш) или сохранять авторский порядок (семантически значимый).

### 8.4. Copy (0x43) — Копия чужой записи

Механизм реакций: пользователь не может писать в чужой блокчейн. Чтобы выразить отношение к чужой записи — нужно скопировать её к себе.

```
Copy = {
  "t":      0x43,
  "source": Ref    // ссылка на оригинальную запись в чужом блокчейне
}
```

### 8.5. Reaction (0x44) — Реакция

Выражение отношения к записи. Реакция всегда указывает на `Copy` (чужая запись) или на собственную запись.

```
Reaction = {
  "t":      0x44,
  "target": Ref,     // ссылка на Copy или на свою запись
  "value":  Int      // int8_t: -128..+127
}
```

**Семантика значений:**

| Диапазон | Смысл |
|----------|-------|
| -128..-64 | Сильное несогласие / ошибочность |
| -63..-1 | Частичное несогласие |
| 0 | Нейтрально / зафиксировано без оценки |
| +1..+63 | Частичное согласие / полезно |
| +64..+127 | Сильное согласие / важно |

**Правило одной реакции:** на один `target` — одна активная `Reaction`. При изменении оценки добавляется новый блок с новой `Reaction` на тот же `target`; агрегаторы учитывают только последнюю (по порядковому индексу блока в ветке, не по `timestamp_claimed`).

### 8.6. Профиль и потребности — теговая конвенция над Concept (решает records.md §14.6)

Самоописание участника (навыки, потребности, желания) выражается **не отдельным протокольным типом, а обычными `Concept`-ами** с зарезервированными тегами. Мотив: профиль — это «любая информация», он должен жить на уровне идей, а не протокола (records.md §14.6). Экономические `Specialty`/`Worker`/`Grade` (records.md §9) — отдельный слой про расчётные ставки; профиль-концепты — про «кто есть / кому что нужно / кто чего хочет», их можно связать через `ConceptLink`.

**Модель (решение 2026-07-13): атомы + опциональная карточка.** Каждый факт профиля — отдельный `Concept`-блок (легко дополнять и обновлять по одному, на каждый можно `Copy`+`React`). По желанию участник группирует их в `Composite` «карточку профиля» — аккуратную единую точку входа; экспорт (records.md §13) всё равно сканирует по тегам и не требует карточки.

**Фасет — обязателен.** Ровно он делает `Concept` фактом профиля; без него это обычная идея, и экспорт её не видит.

| Фасет | Значение |
|-------|----------|
| `kind:skill` | навык / профессия, которыми владею |
| `kind:need` | насущная потребность / запрос |
| `kind:aspiration` | профессию хочу освоить |
| `kind:industry` | отрасль хочу развивать |
| `kind:hobby` | хобби / что люблю делать |
| `kind:obstacle` | что мешает закрыть потребности |

`kind:` задаёт **отношение** участника к записи каталога, а префикс слага (`prof.`/`need.`/`ind.`/`hobby.`) — из какого каталога она взята: одна запись `cat:prof.welder` под `kind:skill` значит «умею варить», под `kind:aspiration` — «хочу научиться». `Concept.text` несёт живое человеческое описание.

**Базовые характеристики (принято 2026-07-13).** Минимум, достаточный для осмысленной стыковки. Профиль, который долго заполнять, не заполнят — поэтому набор намеренно узок; всё остальное добавляется потом, бесплатно, новыми тегами.

| Тег | Значение |
|-----|----------|
| `cat:<slug>` | запись каталога (records.md §8.7), напр. `cat:prof.electrician` |
| `geo:<lat>,<lon>` | где это актуально. Проект всепланетарный: ремонт машины важен в конкретном месте |
| `r:<km>` \| `r:global` | радиус актуальности. Он же — ручка приватности: больше радиус = обезличеннее |
| `remote:yes` \| `no` | можно ли удалённо (консультация, онлайн-работа → часто `r:global`) |
| `horizon:now` \| `3m` \| `1y` \| `3y` \| `5y` | горизонт потребности/желания |
| `retrain:yes` \| `no` \| `maybe` | готовность осваивать новую профессию |
| `grade:<текст>` | заявленный разряд — вольное заявление о себе; экономического `Grade` больше нет (records.md §9.2), квалификацию показывает принятая работа по осям (records.md §14.4) |
| `exp:<лет>` | стаж по навыку |
| `capacity:<часов/нед>` | сколько может отдать труду |
| `urgency:low` \| `normal` \| `high` | срочность потребности |

**Приватность через огрубление.** Точность координаты выбирает сам участник: `geo:55.7` — район, `geo:55.7512` — дом. Кто хочет обезличиться — огрубляет координату и увеличивает радиус.

**Резерв на будущее** (не обязательны, вводятся по мере надобности — код их уже пропускает насквозь, см. records.md §13): `mobile:yes|no` (готов выезжать) · `hours:09:00-18:00` · `days:mon-fri|weekends` · `lead:<дней>` (за сколько предупредить) · `duration:<часов>` (объём работы) · `deadline:<unix>` · `season:summer|winter` · `cert:<название>` (допуск, напр. «до 1000В») · `tools:yes` (со своим инструментом) · `team:<n>` (может привести бригаду) · `teach:yes` (готов обучать этому) · `barter:ok` (встречный обмен навыком) · `free:yes` (безвозмездно) · `price:<трудочасов>` (ожидаемая оценка) · `lang:ru,en` · `for:children|elderly` · `mind:tech|humanities` (склад ума).

```
Concept{ text:"Электромонтаж, 8 лет, допуск до 1000В",
         tags:["kind:skill","cat:prof.electrician","geo:55.75,37.62","r:30",
               "grade:4","exp:8","capacity:20","retrain:maybe"] }
Concept{ text:"Нужно заменить проводку в двушке, ищу электрика",
         tags:["kind:need","cat:need.electrical","geo:55.76,37.60","r:10",
               "horizon:now","urgency:high"] }
Concept{ text:"Консультирую по бухгалтерии, где угодно",
         tags:["kind:skill","cat:prof.accountant","remote:yes","r:global"] }
```

**Жизненный цикл потребности — словарь сделки (решение 2026-07-15, ИР-006 шаг 2).** Весь путь от найденного матча до закрытой потребности выражается обычными `ConceptLink` — ни одного нового протокольного типа:

| Связь | from → to | Чья цепь | Смысл |
|-------|-----------|----------|-------|
| `kind:"берусь"` | свой навык → чужая потребность | исполнителя | заявка на исполнение (решает records.md §14.7) |
| `kind:"исполняет"` | своя `WorkRecord` → потребность | исполнителя | эта работа сделана под эту потребность; **много-ко-многим** — несколькими связями (три захода на одну потребность; один заказ на две) |
| `kind:"закрыто"` | своя `Acceptance` → своя потребность | заказчика | авторитетное снятие: заодно фиксирует, **чем** закрыто |

**Все связи необязательны.** Сделка — не жёсткий конвейер, а потребность с хвостом ссылок на неё: прямая сделка без постнутой потребности, работа на склад без покупателя, закрытие без работы в системе (помог сосед) — законные состояния, а не ошибки. Обещание (`Pledge`) — тоже необязательное звено: оно про финансирование наперёд (records.md §11.3), а не про личность сделки. Стадия сделки выводится из наличных звеньев.

**Закрыть факт может только его хозяин:** закрывающая связь обязана лежать в той же цепи, на которую указывает (`to.chain` == автор блока) — иначе чужой мог бы «снять» вашу потребность. Если закрывать нечем (работа вне системы), допускается прежнее самозамыкание `from == to` (потребность → она же). Закрытый факт помечается в экспорте (`"closed": true`) и выпадает из стыковки.

### 8.7. Универсальные каталоги профессий и потребностей

Курируемые справочники, из которых участник выбирает запись (`cat:<slug>`), а не изобретает формулировку — так самоописания машинно-сопоставимы. Хранение (решение 2026-07-13): **гибрид** — версионируемые JSON-файлы в репозитории (`docs/catalogs/`), которые агрегатор раздаёт по `GET /catalog`; позже, при необходимости, каталог можно заякорить как `Concept`-ы на референс-цепи проекта. Формат и наполнение — в `docs/catalogs.md`.

### 8.8. Черновик: готовит писарь, подписывает хозяин (решение 2026-07-13)

Нетехническому участнику (электрику, швее, повару) сырой CLI недоступен. Поэтому записи за него может подготовить **помощник — писарь, бухгалтер или ИИ**. Разрез проходит по границе `payload`: содержимое записи не требует ни ключей, ни состояния цепи; подпись требует и того, и другого.

**Черновик** — key-free JSON со списком записей. Он **не несёт полномочий**: его можно слать любым каналом и генерировать коммерческой моделью. Ценность появляется только когда хозяин применяет его своим ключом — `bc apply --draft FILE`, где **один блок = одна подпись** (blockchain.md §5).

```json
{ "leaf": 2147483647,
  "records": [
    {"t":"concept","text":"Пошив и ремонт одежды, 12 лет",
     "tags":["kind:skill","cat:prof.tailor","geo:55.75,37.61","r:15","grade:4"]}
  ] }
```

**Белый список — применение «градиента необратимости» (ИР-002).** В черновике допустимы только полностью обратимые записи без ценности: `Concept`, `ConceptLink`, `Composite`. Ценностные и необратимые (`Transfer`, `Pledge`, `Acceptance`, `Redemption`, операции с ключами) **отвергаются на входе** — не бдительностью читателя, а структурно. Поэтому перевод не может спрятаться среди тридцати фактов профиля. Обоснование асимметрии: ошибочно подписанный `Concept` снимается следующей записью (records.md §8.6), а ошибочно подписанный `Transfer` необратимо двигает ценность.

**Почему пакет, а не поштучное подтверждение.** Каждый блок и так несёт свою подпись — «подписать много блоков одной подписью» невозможно физически. Вопрос лишь в человеческом просмотре, и здесь пятнадцать подтверждений подряд **учат жать «да» не читая**: усталость от подтверждений — сама по себе уязвимость. Поэтому: потолок в **20 записей** на черновик, **полный рендер каждой** записи без обрезки (`--dry-run`), одно осознанное подтверждение. Отклонение черновика — всегда целиком, включая безобидные записи.

Ценностные записи, когда их допустят в черновики, подписываются **по одной**, с ручным переподтверждением суммы и получателя; смешанный черновик запрещён.

### 8.10. Consent (0x46) — Согласие на чужую запись

Односторонняя запись «я не против — действуй» в **своей** ветке (ИР-012, форма «каждый пишет у себя», решение участника 2026-10-10). От пломбы (`records.md §8.9`) отличается смыслом: пломба говорит «я видел», согласие — «я согласен». Отказ пишется тем же типом (`agreed = false`), и это нарочно: **и согласие, и отказ равно остаются в истории подписавшего**.

```
Consent = {
  "t":      0x46,
  "target": Ref,      // с чем согласен: цепь и хеш записи
  "agreed": Bool,     // true — согласен, false — против
  "note":   Text      // чем именно; может быть пустым
}
```

**Общего объекта «решение артели» не образуется.** Собрался ли порог — **вычисляемый факт** из N подписанных записей, как признанность сделки (`records.md §9.5`): агрегатор складывает их в `DealsOnTable::consents`, витрина отдаёт `GET /consents/<хеш>`, а судит читатель. Иначе общий объект пришлось бы кому-то подписывать — и вернулся бы вопрос «кому», которого ИР-012 и избегает.

**Правила:**

- `target` обязан называть и цепь, и хеш (отказ кодека).
- **Себя не спрашивают:** согласие на запись своей же цепи не считается — подпись под своей записью и есть согласие.
- **Позднее слово цепи отменяет прежнее** (по времени блока), как у реакций (`records.md §8.5`): передумать можно, и это видно.

**Зачем это нужно.** Редкие дорогие решения об общей вещи — ремонт, продажа её самой, выпуск календаря смен (ИР-013) — держатель составляет записью **в своей цепи**, а совладельцы подписывают согласие у себя. Иначе и не выразить: перенос стоимости засчитывается только в записи самого владельца, поэтому «выпустить вместе» означает «один составил, остальные согласились». Рутина же согласий не требует вовсе — в своих оплаченных моточасах никто никого не спрашивает (ИР-013).

### 8.9. Attest (0x45) — Пломба: «я видел это состояние»

Односторонняя запись (по таблице `blockchain.md §5`) в ветке **самого свидетеля**: заверение существования или содержания чужого блока. До 2026-10-10 пломба была строкой в отдельной таблице `seals`; решение участника — **держать её блоком в своей ветке** (`blockchain.md §7.4` v2), и из формы следует всё остальное: у пломбы есть место во времени, её можно сосчитать, и чья она — видно по адресу блока, без привязки ключа к цепи.

```
Attest = {
  "t":      0x45,
  "target": Ref,      // что заверено: цепь и хеш блока
  "mode":   Text,     // "blind" — видел, что блок существует;
                      // "open"  — видел содержание (blockchain.md §7.1)
  "note":   Text      // что именно видел; может быть пустым
}
```

**Правила:**

- `mode` — только `"blind"` или `"open"`; третьего нет, и это утверждение свидетеля о том, что он видел.
- `target` обязан называть и цепь, и хеш: пломба без адресата ничего не заверяет (отказ кодека).
- **Себя не заверяют.** Пломба на запись своей же цепи не считается: своя подпись под своей записью не добавляет ничего. Кодек этого не видит (он не знает, кто пишет), поэтому отказывает клиент, а витрины такие пломбы пропускают.
- **Ни работник, ни плательщик не свидетели** при счёте заверенности сделки: первый заверял бы себя, у второго подпись и так стоит в приёмке (`records.md §12.11`).
- Повторная пломба той же цепи на тот же блок ничего не меняет — витрины считают **цепи**, а не записи.

**Что видно в следе** (`records.md §12.11`, `GET /footprint/<цепь>`): `labor_sealed` и `attester_chains` — сколько часов принятого труда заверили посторонние цепи и какие именно; `vouched_hours`/`vouched_works` — сколько чужого труда заверила сама эта цепь. Второе и делает заверение небесплатным: ложная пломба остаётся в истории свидетеля.

Со-подписи слияний (`blockchain.md §6.4`) — не пломбы: это «мы согласились», а не «я видел», и живут они в таблице `seals` со своим складом (`sync.md §7.2`).

## 9. Трудовые записи (0x50–0x5F)

### 9.1. Specialty (0x50) — снята (2026-09-11)

Запись называла специальность слагом каталога и служила глобальным ключом ставок: пока это был свободный текст, «Электрик», «электрик» и «Электромонтёр» давали три разные ставки. **Снята вместе со ставками специальностей (ИР-022 шаг 11).** Цена работы расписана по осям в самой приёмке (`records.md §9.5` v4), и сеть публикует цены осей, а не специальностей (`records.md §11.2` v5), — ключа, который надо было держать единым, больше нет. Кем работал человек, говорит вольное поле `title` записи о труде (`records.md §9.4`) — для людей, по нему ничего не считается. Номер `0x50` не переиспользуется.

Слаги каталога профессий остаются в профилях (`cat:prof.*`, `records.md §8.6`) — для поиска и стыковки, а не для цены.

### 9.2. Grade (0x51) — снята (2026-09-11)

Разряд 1–6 специальности. Сначала он ушёл из ключа ставки (2026-09-10): час мастера выходил дороже по одному званию, сверх того, за что платила сама сделка. Потом — целиком (ИР-022 шаг 11): звеном «работа → специальность» ему быть больше незачем, а квалификацию показывает принятая другими работа по осям (`records.md §14.4`). Что делает час мастера дороже, называется в разбивке — отдельной осью на каждое умение («работа под напряжением 400 В» рядом с «220 В»; замер — `records.md §11.2`). Номер `0x51` не переиспользуется.

### 9.3. Worker (0x52) — снята (2026-09-11)

Запись связывала цепь со списком её разрядов и в коде не использовалась. Работник — это цепь, подписавшая запись о труде. Номер `0x52` не переиспользуется.

### 9.4. WorkRecord (0x53) — Запись о труде

Один акт труда. Трудочасы **не возникают** при создании записи — только после сделки: перевода с приёмкой внутри, по адресу продавца (records.md §9.5).

```
WorkRecord = {
  "t":      0x53,
  "action": Text,        // описание работы
  "time": {
    "start": Int,        // Unix timestamp начала
    "hours": Float       // затраченное время в часах
  },
  "inputs": [{
    "resource": Ref | Text,
    "qty":      Float,
    "unit":     Text
  }, ...]?,
  "outputs": [{            // выход — партия (v5, ИР-023)
    "resource": Ref | Text,
    "qty":      Float,
    "unit":     Text,
    "share":    Float?,     // v5: доля часов работы в этом выходе, Σ = 1 (совместный выход)
    "price":    Float?,     // v6: ценник — трудочасы за всю партию, закреплён при изготовлении
    "units":    [Text, ...]?, // v6: номера единиц — партия со штучным учётом, qty = их число
    "life":     Float?      // v7: срок службы, дни — норма износа при аренде (records.md §9.8 v6)
  }, ...]?,
  "carry": [{              // v2 (ИР-011): перенос стоимости средств производства
    "src":     Ref,        //   Tool (records.md §10.2) или партия Material (records.md §10.1)
    "used":    Float,      //   израсходовано: часы работы инструмента / количество материала
    "carried": Float,      //   перенесено в эту работу, трудочасов
    "seq":     Int,        //   звено нити переноса записи src
    "prev":    Ref?,       //   предыдущее звено (у первого отсутствует)
    "after":   Float       //   собрано по записи src после звена; инвариант: after ≤ cost
  }, ...]?,
  "title":  Text?,        // «кем работал» — вольный текст для людей (ИР-022 шаг 11)
  "customer": Bytes(32)?, // v3 (ИР-023): заказчик — результат отпущен ему этой же записью
  "thread": {             // v4 (ИР-023): звено товарной нити цепи
    "seq":  Int,          //   на единицу больше наибольшего из prev; у первого звена 0
    "prev": [Ref, ...]    //   предыдущие звенья: у первого — ни одного, два и больше — слияние веток
  }?,
  "axes": [{"axis": BlockPath, "share": Float}, ...]?,  // v4: предложенная разбивка часов, Σ share = 1
  "improves": Ref?,     // v6 (ИР-015): работа над своей покупкой — ремонт, наладка; выходов у неё нет
  "spends": [{          // v7 (ИР-023): расход своей продукции в это изделие
    "work": Ref,        //   своя запись труда, чей выход израсходован
    "lot":  LotLink     //   звено подниточки её партии — как у продажи порции
  }, ...]?
}
```

**Работник — цепь, подписавшая запись (ИР-022 шаг 11).** Ссылки на разряд и специальность нет: чем была работа, говорит разбивка её цены в приёмке (`records.md §9.5`). `title` — вольный рудимент для людей («электрик, 5-й разряд»), по нему ничего не считается; пустой поля не занимает. Ключ 1 (прежний `agent`) снят и не переиспользуется.

**Заказчик (v3, 2026-09-14, ИР-023).** Работа на заказ несёт `customer` — цепь, с которой договорились заранее: рождение результата и его отпуск в одной записи, отдельный отпуск (records.md §9.8) не нужен. По умолчанию поля нет (решение участника: получатель указывается только при предварительной договорённости) — работа на склад или без договорённости отпускается потом записью `Release`. Засчитывается только сделка того, кому продавец отдал результат (records.md §9.5). CLI: `bc work log --for ЦЕПЬ`; `bc deal work` ставит заказчиком хозяина потребности (`--for` — если платит другой).

**Товарная нить: звено труда (v4, 2026-09-14, ИР-023, пункт 5).** Каждая работа — звено одной на цепь товарной нити: `thread.seq` на единицу больше наибольшего из `prev`, у первого звена `seq = 0` и предыдущих нет (другого кодек не пишет и не читает; `prev` — по возрастанию, без повторов). Нить пишется из любой ветки; две ветки, продолжившие одно звено, не видя друг друга, — форк, звено с двумя предыдущими сводит их. Правила одни для агрегатора и клиента (`records::check_labor_thread`):

- **Одни и те же часы не продаются дважды.** Работа заявляет интервал `[start, start + hours·3600)`; две работы цепи с пересекающимися интервалами (стык — не пересечение) — доказательство, подписанное самой цепью. Какая из двух фиктивна, не узнать, поэтому сделки ни по одной не входят в статистику; оплата при этом состоялась — продавец её адресовал (records.md §9.5).
- **Форк судится мягко** (решение участника 2026-09-12): звено говорит только «я работал с 10 до 18» и ничего не утверждает о других, поэтому форк без пересечения — не обман.
- **Работа вне нити к сделке не признаётся**: её покупатель не мог увидеть, не проданы ли её часы. Заявлены они всё равно — пересечение с ней портит и звено нити.
- **Будущих часов не заявляют** (v5, решение участника 2026-09-16): работа, кончающаяся позже, чем записан объявивший её блок, — вне нити (`ahead` в `LaborThread`), и сделка по ней не в счёт. Проверить такую работу не может никто — этих часов ещё не было, — а место работы, которую ещё предстоит сделать, она бы заняла. Дата блока — слово самой цепи, но она не убывает (blockchain.md §9.4), поэтому «записаться вперёд» значит увести в будущее всю свою цепь, и это видно всем.
- **Битое звено** — `seq` не на единицу больше предыдущих, предыдущее из чужой цепи или не звено — вне нити. Предыдущего нет на столе — пробел, а не вина: звено остаётся в нити.

`axes` — **предложенная разбивка** часов по осям, «труд по осям», ещё никем не подтверждённый: доли положительны и в сумме дают 1. Покупатель подтверждает её или пишет свою в приёмке (records.md §9.5); `bc accept` без разбивки берёт предложенную. Непроданные звенья нити — **ещё не подтверждённый труд**, видный по осям в любой момент (`GET /thread/<цепь>`, `bc thread`).

CLI (`bc work log`, `bc deal work`) ведёт нить сам: звено ставится после всех вершин, которые видит устройство (несколько — слияние). Без `--start` работа считается только что законченной (`start = сейчас − часы`). Клиент ничего не угадывает (v5, решение участника 2026-09-16): заняты эти часы другой работой цепи — запись отклоняется, а клиент называет ближайшее свободное окно; время работы ставит человек. Работу, кончающуюся в будущем, клиент не пишет вовсе. `bc accept` не платит за работу вне нити, на чужих часах или из будущего (`thread_state` в `GET /work/<цепь>/<хеш>`: `unthreaded`, `broken`, `crossing`, `ahead`). Звенья отпусков и списаний партий — подниточки партий (records.md §9.8 v2, records.md §9.9).

**Выход — партия (v5, 2026-09-14, ИР-023, пункты 1–3).** Каждый выход работы — партия; её идентичность — путь к записи труда и номер выхода (серийник, ИР-023, пункт 1). Продаётся партия целиком (заказчиком или отпуском без порции) или порциями — звеньями подниточки партии (records.md §9.8 v2). Одна работа с несколькими выходами (лесопилка: доски и опилки) делит часы между ними долями `share` с суммой 1 — объявляет производитель, подтверждает покупатель; без долей порцию такой работы не оценить. `price` — **ценник** (v6, решение участника 2026-09-15, ИР-023, вопрос 11): трудочасы за всю партию, закреплённые при изготовлении. Клиент считает его из k по ценам осей **дня производства** (вопрос 2): часы × доля выхода × Σ цен предложенных осей × k — по агрегату, опубликованному в тот день (`GET /economy/rates?date=`; нет его — по сегодняшним). Порции продаются по ценнику, «бери или нет» (records.md §9.8 v3); снижение — переоценка вниз. Ценник записывается числом, а не k, чтобы условия порции проверялись по одним записям продавца, без чьих-то цен. `units` — **номера единиц** (v6, вопрос 10): партия со штучным учётом — велосипеды с номерами рам, табуреты с клеймом; количество — число номеров, номер не повторяется. Серийник единицы — путь к записи рождения, номер выхода и её номер. Доля, ценник и номера бывают только у выходов — у входов кодек их не пишет; ключ 4 (`k` v5) снят и не читается. `life` — **срок службы** (v7, решение участника 2026-09-15, ИР-023, пункт 8): дни; объявляет мастер при изготовлении, до всякой аренды. По нему считается износ, которым оплачивается аренда: прямая от рождения вещи — конца работы — до конца срока (records.md §9.8 v6). CLI: `--output ИМЯ:КОЛ:ЕД[:ДОЛЯ[:ЦЕНА[:НОМЕРА[:СРОК]]]]`, ЦЕНА — число трудочасов или `k=K`, СРОК — срок службы в днях.

**Машино-часы: аренда по счётчику (v8, решение участника 2026-09-13, ИР-023, пункт 9).** Второй способ сдать вещь — не отдавать её вовсе. Владелец пишет запись **без часов труда** (`hours = 0`), в которой есть только перенос: звено нити переноса на снятые по счётчику машино-часы и выход «машино-часы» в них же. Вещь и риск поломки остаются у владельца, арендатору не нужен кредит на всю её стоимость. Цену такой записи никто не называет: она равна записанному износу (`records::is_machine_hours`, `records::meets_machine_hours`), и приёмка её — чистый перенос без разбивки по осям: труда в ней нет, разбивать нечего. Это третье и последнее исключение из «приёмки без разбивки не существует» (ИР-022). Приёмка с трудом по такой записи ничего не завершает — часов в ней никто не работал. Показания счётчика подписывают обе стороны: владелец — самой записью, арендатор — приёмкой. Дальше арендатор заводит купленные часы материалом (`bc material add --paid ПОКУПКА`, records.md §10.1 v3) и тратит их в свои работы, как всякий купленный материал. Нить труда такая запись не занимает: её интервал пуст. CLI: `bc hire ИНСТРУМЕНТ --to ЦЕПЬ --machine-hours N [--meter «1240→1244»]`.

**Расход своей продукции в своё производство (v7, решение участника 2026-09-20, ИР-023).** `spends` — звенья подниточек своих партий: сколько своей продукции ушло в это изделие. Деталь при этом **не становится товаром с ценой**: цену своей вещи назначал бы сам работник, и её никто не подтверждал. В изделие приходит **труд** детали — часы работы-источника, приходящиеся на израсходованное (`records::spent_hours` = доля партии × её часы), — и подтверждает их покупатель готового изделия своей разбивкой по осям. Часы каждой работы считаются **по ценам её дня производства** (решение участника 2026-09-20, то же правило, что для порции партии: труд был тогда, а в момент продажи его может и не быть). Перенос в такой приёмке — свои звенья переноса плюс доля переноса израсходованных работ: купленные материалы, вложенные в деталь, доходят до цены изделия. Звено расхода считается в той же подниточке, что продажи и списания: израсходованного уже не продать, а сверх партии не израсходовать (`records::check_lot`). Сделка по изделию признаётся, только если работы-источники сами в счёт и их звенья сходятся — иначе одни и те же часы продали бы дважды. CLI: `bc work log --spend РАБОТА:КОЛИЧЕСТВО[:ВЫХОД]`; `bc accept` по умолчанию складывает цену из часов всех работ, свои условия покупателя — как всегда.

**Работа над своей покупкой (v6, решение участника 2026-09-16, ИР-015).** `improves` — ссылка на свою покупку, над которой работали: ремонт, наладка, перетяжка. Нового изделия такая работа не рождает — дорожает сама вещь, — поэтому выходов у неё нет, и кодек их не пишет. Оплачивается она той же сделкой, которой вещь выкупают назад (records.md §9.8 v7): иначе ремонт и выкуп были бы двумя независимыми сделками, и ремонтник мог остаться с вещью и неоплаченным трудом. CLI: `bc work log --improves ПОКУПКА`.

**Нить переноса (v2, ИР-011).** Стоимость инструмента и материалов переносится в продукцию той же механикой, что нить эмиссии (economy.md §4.3): каждое использование — звено `{seq, prev, after}`; нить **одна на запись средства производства на всю цепь** — звенья могут писаться в любых ветках (`prev` — Ref, работает через ветки), но линейность обязательна: два звена с одним `prev` — эквивокация, двойное списание одного средства по параллельным веткам ловится как форк нити. Правила признания звена:

- `carried = min(used / ёмкость × cost, cost − собрано_до)` — доля **недособранной** стоимости; ёмкость для инструмента — ресурс `life` в часах работы, для партии материала — её размер `qty`;
- `after = собрано_до + carried`, и всегда `after ≤ cost` — за всю жизнь записи переносится не больше вложенного (аудируемый инвариант, проверяется по последнему звену за O(1));
- при `собрано_до = cost` перенос **обнуляется принудительно**: использование пишется дальше (часы и расход — для статистики и износа), но `carried = 0` — полностью амортизированное средство удешевляет продукцию автоматически; продолжение переноса было бы денежным насосом (economy.md §4.2 `economy.md`).

Часы работы инструмента (`used`) заявляет владелец в подписанном слоте — как и часы собственного труда; завышение видно заказчику в разбивке приёмки (решение бинарное), занижение — подарок заказчику за свой счёт.

### 9.5. Приёмка — поле `Transfer.accept` (была запись Acceptance 0x54)

Сертификат качества и **оценка стоимости** работы. С 2026-09-14 (ИР-023) приёмка — не отдельная запись, а поле `accept` перевода, которым покупатель за неё платит (records.md §11.1 v5): **оценка и оплата подписываются одной записью**. Поэтому оплата равна оценке по построению (records.md §12.8), а платит тот, кто принимает, — «платит один, принимает другой» записать нельзя (records.md §12.9). Кто принял и когда — `from` и `timestamp` самого перевода. Отдельный тип 0x54 снят и не переиспользуется; обратной совместимости нет (решение участника: часы пока тестовые).

```
accept = {                    // поле Transfer (records.md §11.1), вложенная карта
  "work":        Ref,         // ссылка на WorkRecord — в цепи того, кому платят (`to`)
  "quality":     Text,        // результат проверки: "пройдено", "отклонено", ...
  "hours_raw":   Float,       // фактические часы из WorkRecord
  "labor_units": Float,       // цена живого труда; по умолчанию hours_raw × Σ цен названных осей × k
  "axes":  [{"axis": BlockPath, "units": Float}, ...],  // v4 (ИР-022): разбивка цены, обязательна
  "carried_units": Float?,    // v2 (ИР-011): перенесённая стоимость = Σ carried
  "norm":        {            // v3 (economy.md §2б): нормировщик, при котором оценена
    "agg":  Bytes(32),        //   работа — чтобы историческая оценка читалась однозначно
    "date": Int,              //   (цепь агрегатора + дата + W использованного DailyAggregate)
    "W":    Float
  }?,
  "like":  Ref?,              // ИР-022 шаг 11: сделка-образец — «такая же работа, как та»
  "release": Ref?,            // ИР-023: отпуск продавца на имя плательщика (records.md §9.8)
  "buyback": {                // v5 (ИР-023, пункт 8): заранее подписанный возврат (records.md §9.8)
    "to":    Bytes(32),       //   адресат (ключ 0)
    "until": Int,             //   срок (ключ 2; ключ 1 — названная цена возврата v5 — снят)
    "wear":  1?,              //   v6: аренда — цена возврата за вычетом износа по норме
    "deposit": 1?             //   records.md §9.8 v9 (ключ 4): залог — оплата заморожена у продавца до срока
  }?
}
```

Если продукция не дошла до получателя или не прошла проверку — сделки нет: ни приёмки, ни оплаты. Стоимость такой продукции равна нулю.

**Перенесённая стоимость (v2, ИР-011).** Если принятый `WorkRecord` несёт `carry` (records.md §9.4), приёмка фиксирует и вторую составляющую цены: `carried_units` = Σ `carried` по звеньям переноса (расхождение — приёмка не признаётся; тот же паттерн «хранится явно, проверяется на равенство», что `labor_units`). **Потолок оплаты** (records.md §12.8 «=») — `labor_units + carried_units`. В цены осей records.md §11.2 входит **только** `labor_units`: перенесённая стоимость — овеществлённый труд прошлых периодов и не должна искажать цену живого труда (тот же принцип, что скидки на б/у, economy.md §5б). Строгая эквивалентность соблюдена: перенос — это когда-то *принятый* труд (покупка `paid` заверена приёмкой; декларация `est` помечена и дисциплинируется бинарным отказом заказчика).


**v4 (ИР-022): цена, расписанная по осям.** `axes: [{axis, units}]` — сколько трудочасов цены ушло на каждую ось; Σ`units` обязана в точности равняться `labor_units`.

**`axis` — это `BlockPath`, а не слаг.** Слаги сталкиваются, и выбирать между двумя цепями, назвавшими свою ось `danger`, значило бы чьё-то решение — а места для таких решений здесь нет. Путь ведёт к записи, которая ось **определяет**, поэтому пользоваться осью и указывать на её аргумент — одно и то же действие: по пути до определения можно дойти руками, а хеш показывает, что по этому адресу лежит всё ещё тот самый блок (`records.md §4`, BlockPath). Ссылка, путь которой ведёт не к блоку своего хеша, в книге осей учитывается, но видна (`broken_paths`).

**Приёмки без разбивки НЕ СУЩЕСТВУЕТ** — кроме перепродажи, где живого труда нет и разбивать нечего (records.md §9.8 v4). Кодек отказывается её писать: цена без объяснения — это второй вид записи там, где должен быть один, и вся путаница от того, что их два. Сумма проверяется клиентом до подписи (`bc accept`), а агрегатором — до зачёта в книгу осей.

Это и значит «разбивка на уровне протокола»: объяснение цены подписано **вместе с ценой, в одной записи**. Нельзя принять сделку, а потом вспомнить удобную историю про неё. **Невязки нет** не потому, что модель хорошо ложится, а потому что складывать нечего сверх названного; ничего не выводится — значит нечего и подгонять.

Разбивка, не сходящаяся с ценой, не засчитывается: она описывает какую-то другую сделку.

Оси «прочее» протокол не предлагает: чего не можешь назвать — назови (`records.md §11.12`).

**Образец — «такая же работа, как та» (ИР-022 шаг 11).** Приёмка может назвать `like` — более раннюю приёмку, чью разбивку повторяет. Разбивка при этом выписана целиком в `axes`: `like` говорит лишь, откуда она, и цена со своим объяснением по-прежнему подписаны в одной записи. Клиент берёт доли у образца (`bc accept --like REF`), если сделка не называет своих. Приёмки, связанные `like`, образуют **семьи**, из которых складывается облако работ (`records.md §11.7`): «профессия» — это описание работы, которое люди раз за разом повторяют, а не строка справочника.

**Результат достаётся тому, кому его отдал продавец (2026-09-14, ИР-023).** Сделка — атомарная пара: продавец называет покупателя, покупатель принимает и платит. Назвать покупателя можно двумя способами: работа на заказ несёт `customer` (records.md §9.4) — рождение результата и его отпуск в одной записи; готовый результат отпускается записью `Release` на имя покупателя, со сроком (records.md §9.8). Сделка **адресована**, если её платит заказчик работы или она завершает живой отпуск на имя плательщика (`accept.release`, `timestamp < expires`). Один результат — одна признанная сделка: иначе часы работы вошли бы в цены осей дважды, перенос средств производства оплатился бы дважды при одном звене нити переноса, а квалификация сосчитала бы одну работу как «приняли две цепи». Правило одно для агрегатора и клиента (`records::addressed_to`, `records::recognize_deals`):

- сделка — **оферта, пока продавец её не принял** (records.md §11.13, economy.md §4.4): до его ответа она не двигает ничего; отвергнутая, просроченная или оплаченная бумагой, которой у плательщика не было, — не случилась вовсе и не мешает сделке, которая её заменит;
- сделка **не по адресу ничтожна** — нет ни приёмки, ни оплаты (взаимная ничтожность, economy.md §8.12). Получатель такие часы не принимает (`bc transfer recv`), денежные и статистические витрины агрегатора их не считают (`/deals`: `unaddressed`). Поэтому посторонний не может ни погубить чужую сделку, ни сделать подарок под видом оплаты чужой работы;
- из адресованных сделок одного покупателя признаётся первая (по `timestamp`, при равенстве — по хешу); остальные — **повтор**: часы ушли, переплата видна, в статистику не входят;
- адресованные сделки **двух и более покупателей** — продавец отдал один результат дважды: не признаётся ни одна (`/deals`: `oversold`), и оба адреса подписаны им самим;
- адресованная сделка по работе **вне нити труда или на часах, заявленных и другой работой цепи** (records.md §9.4 v4) — оплата состоялась, но в статистику не входит: эти часы могли продать дважды (`records::DealClaim::sound`);
- **порция партии — свой результат** (records.md §9.8 v2): у каждой порции своя сделка, сто покупателей хлеба — сто признанных сделок; сделка по порции, чьё звено подниточки не сходится (сверх партии, две продажи из одного остатка), — оплата без статистики; работа, проданная и целиком, и порциями, — двойная продажа; сделка по порции не по ценнику партии ничтожна (records.md §9.8 v3);
- **перепродажа** (records.md §9.8 v4) — приёмка без труда и без разбивки по осям, по доле цены покупки; признаётся, только если покупка держателя состоялась, двигает часы и в статистику труда не входит (множество `resold`). Это единственное исключение из «приёмки без разбивки не существует» (решение участника 2026-09-15): труда в ней нет, разбивать нечего;
- **машино-часы** (records.md §9.4 v8) — аренда по счётчику: в записи владельца нет часов труда, только износ, и цена равна ему;
- **выкуп по заранее подписанному возврату** (records.md §9.8 v5) — перепродажа всей покупки держателя адресату по цене возврата — уплаченному держателем, для аренды за вычетом износа по норме (records.md §9.8 v6), — до срока; признаётся без участия держателя. Покупка по выкупу с адресом без подписанного возврата ничтожна. Держателем бывает и сам мастер — выкупив своё: тогда и продажа мастера бывает перепродажей. Кодек пропускает приёмку одним переносом в его цепь, если она называет отпуск или покупку, а признаёт её агрегатор только как перепродажу или выкуп — оплата работы мастера без разбивки ничтожна (ИР-022).

Прежнее правило (v0.14–v0.15) — «две сделки на работу — не признаётся ни одна» — снято по замечанию участника (2026-09-14): любой, готовый заплатить, мог задним числом лишить силы честную сделку. Теперь погубить сделку может только тот, кто продал. Вместе с правилом снят флаг `bc accept --again`: клиент не пишет ни сделку не по адресу, ни повторную, ни сделку по уже проданному результату (`GET /work/<цепь>/<хеш>` — заказчик, отпуски и сделки работы с их статусом). Остаток — гонка со сроком: покупатель, чей отпуск истёк, может подписать сделку задним `timestamp`, и если продавец уже отпустил результат другому, выйдет двойная продажа. Так может поступить только тот, кого продавец сам назвал; упорядочит `timestamp_witnessed` (sync.md §9) — как отзыв обещания против расчёта (records.md §11.3). Продать одну работу по частям многим покупателям — подниточки партий (ИР-023, пункт 5), следующий шаг.

### 9.7. Coefficient (0x56) — Локальная подстройка ставки

### 9.8. Release (0x57) — Отпуск

Продавец отдаёт результат своей работы названному покупателю (ИР-023, пункт 6). Без отпуска — или заказчика в самой записи труда (records.md §9.4) — сделка по работе ничтожна (records.md §9.5): кому достаётся результат, решает тот, кто его сделал, а не тот, кто готов заплатить.

```
Release = {
  "t":         0x57,
  "work":      Ref,         // своя WorkRecord, чей результат отпускается
  "to":        Bytes(32),   // покупатель — завершить отпуск может только он
  "expires":   Int,         // сделка засчитывается, только если её timestamp < expires
  "timestamp": Int,
  "lot": {                  // v2 (ИР-023): порция одного выхода — звено подниточки партии
    "out":     Int,         //   номер выхода работы
    "qty":     Float,       //   сколько отпущено, в единицах выхода
    "seq":     Int,         //   счётчик звеньев партии
    "prev":    Ref?,        //   предыдущее звено (у первого нет)
    "after":   Float,       //   взято из партии после звена; ≤ размера выхода
    "returns": [Ref, ...]?, //   истёкшие невзятые отпуски этой партии — вернулись в запас
    "units":   [Text, ...]? //   v3: номера единиц, взятые звеном, — у партии со штучным учётом
  }?,
  "holding":   Ref?,        // v4 (ИР-023): своя покупка — перепродажа; work — по-прежнему запись рождения вещи
  "addressed": {            // v5 (ИР-023, пункт 8): выкуп с адресом
    "to":    Bytes(32),     //   адресат — до срока следующая продажа признаётся только ему
    "until": Int,           //   срок
    "wear":  1?             //   v6: аренда — возврат по остатку после износа по норме; адресат — сам сдающий
  }?
}
```

- **Пишется в цепи работника.** Отпуск чужой работы ничего не отпускает: читатели сверяют автора блока с `work.chain`. Отпуск себе кодек не пишет.
- **Завершает отпуск только сделка названного покупателя** — перевод с приёмкой, чей `accept.release` называет этот отпуск (records.md §9.5, records.md §11.1). Сделка ссылается на отпуск и потому пишется после него; обратной ссылки не нужно.
- **Срок — свой у каждого отпуска, по согласию сторон** (решение участника 2026-09-14). Не завершён в срок — отпуск не состоялся, и продавец вправе отпустить результат другому. Сравниваются два значения из цепей — `timestamp` сделки и `expires`, гонок стенных часов нет, как у обещания (records.md §11.3). Отпуск, истекающий не позже собственного `timestamp`, кодек не пишет.
- **О цене отпуск ничего не утверждает**: цену, её разбивку и оплату подписывает покупатель в сделке (records.md §9.5).

**Порция партии — подниточка (v2, 2026-09-14, ИР-023, пункт 5).** Отпуск без `lot` отдаёт результат работы целиком — акт услуги, изделие, весь выход. Отпуск с `lot` отдаёт `qty` одного выхода — партии. Отпуски порций и списания (records.md §9.9) одной партии — её **подниточка**, одна на всю цепь (`prev` — Ref, работает через ветки) и **строгая**, как нить переноса (records.md §9.4): `after` = `after` предыдущего + `qty` − возвращённое, и всегда `after ≤` размера выхода, так что остаток партии проверяется за O(1). Два звена с одним `seq` — две продажи из одного остатка: не признаётся ни одно (решение участника 2026-09-12: партия судится строго, параллельные кассы — делением партии). Отпуск, истёкший невзятым, возвращается в запас следующим звеном — оно называет его в `returns`. Вернуть можно только более ранний отпуск этой партии, истёкший к моменту звена, никем не завершённый и не возвращённый раньше; взят ли отпуск, знает агрегатор, поэтому клиент возвращает только с `--via`. Проверка — `records::check_lot`.

Каждая порция — **свой результат** (records.md §9.5): у неё свои часы — часы работы × доля выхода × `qty` / размер выхода — и та же доля переноса средств производства (`records::portion_fraction`). Работа на заказ продаётся только целиком: результат уже отпущен заказчику; работа, проданная и целиком, и порциями, — двойная продажа.

**Порция со склада — по ценнику, «бери или нет» (v3, решение участника 2026-09-15, ИР-023, вопрос 11).** Торгуются при заказе и при покупке партии целиком — там приёмка по осям, как у любой работы. Порция со склада не оценивается: сделка по ней завершает отпуск, только если платит ровно на условиях партии — часы работы в доле порции, доля ценника (`price` × `qty` / размер выхода) по предложенной работником разбивке и та же доля переноса (`records::portion_terms`, `records::meets_terms`). Иначе она ничтожна, как сделка не по адресу, — отпуск, написанный заранее, не отдаёт порцию по цене, которую назначил покупатель. Поэтому порция отпускается только из партии с ценником и из работы с предложенной разбивкой.

**Партия со штучным учётом (v3, решение участника 2026-09-15, вопрос 10).** У партии с номерами (`units` выхода, records.md §9.4 v6) каждое звено называет номера, которые берёт, — количество звена равно их числу. Номер занят звеном, взявшим его, пока то не вернули; звено с номером, которого в партии нет или который занят, продаёт его дважды и не признаётся. Сыпучее и жидкое — без номеров, порции по количеству.

**Перепродажа — купленное у покупателя (v4, решения участника 2026-09-15, ИР-023, пункт 8).** Купленное — партия покупателя: её количество, номера и стоимость даёт сама покупка (`records::holding_lots`): порция — одна партия, целый результат — по партии на выход со стоимостью по долям выходов, услуга — ничего. Держатель перепродаёт отпуском с `holding` — своей покупкой; `work` по-прежнему называет запись рождения вещи, так что **серийник не меняется**, и история вещи читается подряд: рождение → отпуск → покупка → перепродажа. Звено отпуска — в подниточке покупки, строгой, как у любой партии: больше купленного не перепродать, номер дважды не продать. Приёмка перепродажи — **только перенос**: без живого труда и без разбивки по осям (оси определены при первой продаже, вторая — «бери или нет»), по цене — доле уплаченного держателем, без наценки (`records::resale_price`, `records::meets_resale`); сделка не по этой цене ничтожна. Перепродажа признаётся, только если покупка держателя сама состоялась, и в статистику труда не входит: работа склада и перевозки — отдельный труд (ИР-023, вопрос 1). Списание купленного — `WriteOff` с `holding` (records.md §9.9). CLI: `bc release ПОКУПКА --to ЦЕПЬ --qty Q` (ПОКУПКА — своя сделка, `acceptance ref`), `bc stock` — своё купленное.

**Выкуп с адресом и заранее подписанный возврат (v5, решения участника 2026-09-13…15, ИР-023, пункт 8).** Отпуск с `addressed` — выкуп с адресом: собственность и риск переходят к покупателю, но до `until` его следующую продажу признают только адресату — самому продавцу (хранение, ремонт, аренда) или названному получателю (перевозка). Покупка по такому отпуску завершает его, только если в той же записи — в приёмке покупателя — подписан возврат `buyback`: адресату, на тот же срок и на тех же условиях износа (`records::honours_buyout`); иначе она ничтожна. Адресат выкупает сам, без участия держателя: сделкой перепродажи, чей `accept.release` называет саму покупку держателя, — по цене возврата, до срока (`records::completes_buyback`): это уплаченное держателем, а для аренды — за вычетом износа по норме (v6). Платить можно и бумагой самого держателя: вернувшись к эмитенту, она гасит его долг (records.md §12.10). До срока держатель не может продать купленное никому другому, а после выкупа — никому вовсе: такие отпуски не признаются, а сделка по ним **ничтожна** — часы остаются у покупателя (решение участника 2026-09-16: препятствие видно ему заранее, в самом отпуске, и терять часы не за что; `bc accept` за такое не платит, `bc transfer recv` такую оплату не принимает). Списание потерь — в любое время, риск на держателе. Не выкупил адресат до срока — ограничение снимается, у прежнего владельца остаётся бумага держателя. «Не даёт выкупить» в цепи становится невозможным. Работа держателя — ремонт, перевозка — оплачивается отдельно, как его работа на заказ владельца; передача без собственности в цепи не записывается вовсе (решение участника 2026-09-15). CLI: `bc release … --buyback | --buyback-to ЦЕПЬ [--buyback-days N]`; покупатель подписывает возврат сам (`bc accept`); адресат выкупает `bc accept --work РАБОТА` — возврат находится сам — или `--buyback-of ПОКУПКА`.

**Выкуп с ремонтом — одной сделкой (v7, решение участника 2026-09-16, ИР-015).** Держатель, работавший над вещью (`WorkRecord.improves`, records.md §9.4 v6), получает за труд той же записью, которой адресат её выкупает. Приёмка выкупа тогда называет не рождение вещи, а **работу держателя**: `accept.work` — его запись труда над этой покупкой, `accept.release` — сама покупка (подписанный возврат). Платит адресат: `carried_units` — вещь по норме износа плюс расходники ремонта (перенос из нити переноса работы), `labor_units` с разбивкой по осям — труд держателя, подтверждённый покупателем, как в любой приёмке (`records::completes_buyback` с работой ремонта). Отсюда три следствия. **Вещь дорожает ровно на ремонт**: её новая учётная стоимость у адресата — уплаченное по этой сделке, и дальше она продаётся от неё. **Труд ремонта идёт в статистику** как всякий оплаченный труд: сделка признаётся не переносом, а оплатой работы (источник — сама работа ремонта, «одна работа — одна сделка»). **Ни у кого нет рычага**: адресат не заберёт вещь, не оплатив ремонт, а держатель не получит оплату, не отдав вещь. Не выкупил адресат до срока — ограничение снимается, вещь остаётся у держателя, а неоплаченным остаётся только его труд (принудить к приёмке протокол не может, economy.md §4.2). Выкуп без ремонта прежний — только перенос. CLI: `bc work log --improves ПОКУПКА`, затем адресат `bc accept --work РАБОТА` — работа держателя находится сама (`repair` в `buybacks`) или называется флагом `--repair`.

**Аренда без ренты (v6, решение участника 2026-09-15, ИР-023, пункт 8).** За аренду не платят — возмещают только износ: во время аренды никто не трудился, вещь лишь изнашивалась (ИР-011: чистой ренты нет). Сдают выкупом с адресом на себя с пометкой `wear` (`bc release … --rent`): арендатор платит полную цену вещи — например, своей бумагой, векселем, — и подписывает возврат `buyback` с той же пометкой. Цену возврата не называет никто — ни в отпуске, ни в возврате: это уплаченное держателем за вычетом **износа по норме** — прямой от рождения вещи (конца работы) через срок службы `life`, объявленный мастером при изготовлении (records.md §9.4 v7). Остаётся доля `(срок − возраст при выкупе) / (срок − возраст при покупке)` (`records::residual_share`, `records::buyback_price`). Пример участника: квартира за 100, износ по норме за время аренды — 5. Сдающий выкупает её за 95, возвращая арендатору 95 его же векселя; у сдающего квартира на 95 и остаток векселя на 5, у арендатора долг 5 — ровно то, что он потребил. После возврата у сдающего ровно то, что было, так что сдавать ради дохода смысла нет. Выкуп не по норме ничего не завершает: дешевле нормы — это рента, дороже — бесплатное пользование за счёт сдающего. Поэтому износ нельзя ни раздуть (скрытый перевод часов сдающему), ни спрятать. Вещь без срока службы по норме не изнашивается: сдать её с пометкой нельзя, а без пометки она возвращается по цене покупки — так её отдают на хранение, в ремонт, в перевозку, где ею не пользуются. Износ сверх нормы — поломку — возмещает ремонт: это труд, его оплачивает арендатор как работу на свой заказ. Остаётся «сдать для другого»: арендует один, живёт другой — то же, что дать пользоваться своей вещью, чего блокчейн запретить не может (economy.md §4.2). В цепи износ записан на арендатора, взятка неликвидна и не больше нормы износа. Держатель не участвует и тут: адресат выкупает, когда решит, но задержка ему ничего не приносит — насколько подешевела вещь, настолько выросла бумага арендатора у сдающего.

**Залог (v9, решение участника 2026-10-15, economy.md §8.15).** С офертами (records.md §11.13) выкуп ответа держателя не ждёт, если платит бумагой, на которую тот согласился, подписывая возврат (`records::pre_accepted_buyback`): по умолчанию это его собственная бумага и своя эмиссия адресата (economy.md §4.4). Покупатель может выбрать иное — залог, `buyback.deposit` (ключ 4). Тогда его оплата лежит у продавца замороженной до `until`: до срока первая трата бумаги, пришедшей этой покупкой, — сам выкуп, а трата на постороннее — не бумага (`records::deposit_frozen`, `BillSpend::frozen`): нить векселя рвётся, как при любой лжи. Выкуп из залога ответа не ждёт — держателю возвращается то самое, чем он платил; согласованы залог и бумага держателя. Своя эмиссия адресата при залоге согласована лишь в той доле, в какой оплата была его же бумагой: та часть вернулась к нему домой и умерла с долгом, векселя от неё нет, — ею же он и возвращает, не больше. После выкупа или срока залог свободен. Залог бывает, только когда вещь возвращается самому продавцу (хранение, ремонт, аренда) — оплата лежит у него; при перевозке третьему лицу его нет, кодек такого не запишет. Капитал продавца на срок заморожен — это цена гарантии, и выбирает её покупатель, а продавец принимает такую оферту или отказывает. CLI: `bc accept --deposit`; `bc transfer recv` показывает залог продавцу, `bc wallet` — «в залоге под выкуп до …»; клиент не тратит залог до срока ни на что, кроме выкупа, а выкуп по умолчанию платит согласованной бумагой — бумагой держателя и залогом.

CLI: `bc release РАБОТА --to ЦЕПЬ [--qty Q | --units НОМЕР,...] [--out N] [--days N | --until TS]` (по умолчанию 7 дней; с `--qty` или `--units` — порция: звено подниточки ведёт клиент, больше остатка не отпустит, номер второй раз не продаст); `bc accept` находит живой отпуск на своё имя сам (или `--release REF`) и порцию принимает по ценнику — её часы, цена, разбивка и перенос берутся из партии.

**Смены как номерные единицы (v8, ИР-013, 2026-10-10).** Календарь смен общей вещи — обычная партия с номерами: запись без часов труда с одним переносом (`records.md §9.4` v8) объявляет выходом «смены» с номерами (`2026-11-03`, `вт-04`), а каждая смена уходит порцией этой партии. Отсюда расписание даром: **номер продаётся один раз, возврат его освобождает, двойная продажа — форк подниточки** (`records::check_lot`), свободные смены видны в `bc thread`. Порция машино-часов платит **свою долю записанного износа** — ценника ей не нужно, разбивать по осям нечего (`records::portion_terms`); целиком такую запись покупают по-прежнему за весь износ. Держатель составляет календарь записью в своей цепи (иначе её некому написать — перенос засчитывается только у владельца), а совладельцы подписывают согласие (`records.md §8.10`). CLI: `bc hire ИНСТРУМЕНТ --shifts "ИМЯ1,ИМЯ2" --machine-hours ЧАСОВ_В_СМЕНЕ`, затем `bc release РАБОТА --to ЦЕПЬ --units ИМЯ`.

### 9.9. WriteOff (0x58) — Списание

Часть партии уходит из неё без продажи — испорчена, потеряна, израсходована (ИР-023, пункт 5). Звено той же подниточки, что отпуск порции (records.md §9.8 v2): остаток партии остаётся проверяемым, а потеря — видна в цепи продавца (след, ИР-010; отзыв, ИР-024).

```
WriteOff = {
  "t":         0x58,
  "work":      Ref,         // своя WorkRecord, чей выход — партия
  "lot":       {...},       // звено подниточки: out, qty, seq, prev, after, returns? (records.md §9.8)
  "reason":    Text,        // почему: «подгорели», «бой при перевозке»
  "timestamp": Int,
  "holding":   Ref?         // v2: списывается купленное — своя покупка (records.md §9.8 v4)
}
```

Списанное не продаётся и не входит в ещё не подтверждённый труд — это потерянный труд, и он виден как потерянный. Работа на заказ не списывается: её результат у заказчика. CLI: `bc writeoff РАБОТА --qty Q [--out N] --reason ТЕКСТ`.

## 10. Производство (0x60–0x6F)

### 10.1. Material (0x60) — Партия материала

v2 (ИР-011): материал учитывается **партиями** с переносимым остатком — купленная партия переносит стоимость в продукцию по мере расхода той же нитью переноса, что инструмент (records.md §9.4). Раскладка полей зеркальна `Tool` (records.md §10.2); ёмкость нити — размер партии `qty`.

```
Material = {
  "t":      0x60,
  "name":   Text,
  "unit":   Text,     // "кг", "м³", "шт", "л", "кВт·ч", ...
  "desc":   Text,     // может быть пустым
  "cost":   Float,    // стоимость партии, трудочасов
  "qty":    Float,    // размер партии в unit (ёмкость нити переноса)
  "basis":  Text,     // "paid" | "est"
  "src":    Ref?,     // paid: приёмка покупки — стоимость заверена
  "origin": Ref?,     // предыдущая запись партии (перевыпуск, правила records.md §10.2)
  "note":   Text,     // est: пояснение оценки; может быть пустым
  "lot":    LotLink?, // v3 (ИР-023): звено подниточки своей покупки, которым взята партия
  "days":   Int?      // v4 (ИР-011 v5): календарный срок партии в днях, со дня записи
}
```

**Купленное — в своё производство (v3, решение участника 2026-09-16, ИР-023).** Купленная партия и партия-материал — одно и то же: покупка уже ведёт свою подниточку (records.md §9.8 v4), и запись материала берёт из неё звеном `lot`, как отпуск при перепродаже и как списание. Отсюда два следствия. **Стоимость не объявляют**: у записи с `basis = "paid"` она обязана равняться доле уплаченного за взятое количество — `cost = уплачено × qty / размер купленной партии` (`records::resale_price`); запись с завышенной стоимостью агрегатор не признаёт, и перенос из неё в продукцию не считается — иначе это денежный насос (ИР-011). **Что ушло в производство, то уже не продать**: звенья производства, перепродаж и списаний считаются в одной подниточке, и сумма взятого не может превысить купленное — это проверяет тот же `records::check_lot`. Сводка покупки показывает израсходованное отдельно (`consumed` в `GET /stock/<цепь>`, «в производство» в `bc stock`). Дальше стоимость записи материала расходуется в продукцию нитью переноса (records.md §9.4), как и у оценённой владельцем. CLI: `bc material add ИМЯ --paid ПОКУПКА --qty КОЛ [--out N]`, `bc tool add ИМЯ --paid ПОКУПКА --life ЧАСЫ [--units НОМЕР]` — стоимость и размер берутся из сделки, `--cost` с `--paid` не задают.

**Срок партии (v4, 2026-10-10, ИР-011 v5).** У партии тоже две шкалы: размер `qty` и календарный срок `days` — скоропортящееся изнашивается временем, даже если его не тронули. Износ — больший из двух, правила и формулы те же, что у инструмента (records.md §10.2). CLI: `bc material add ИМЯ --cost N --qty Q [--days D]`.

Природные ресурсы (руда, вода, земля) и энергия **не имеют трудочасовой стоимости сами по себе**. Стоимость появляется только через `WorkRecord` на их добычу или генерацию — либо, в переходный период, через декларированный фиатный эквивалент купленной партии (`est`: цена в валюте / средняя часовая ставка, с пометкой всюду). Мелочь (крепёж, расходники на копейки) в партии не оформляется — сидит в k, как накладные расходы мастера.

### 10.2. Tool (0x61) — Инструмент / оборудование

v2 (ИР-011): инструмент несёт стоимость и расчётный ресурс; износ переносит стоимость в продукцию через `carry` (records.md §9.4).

```
Tool = {
  "t":      0x61,
  "name":   Text,
  "desc":   Text,     // может быть пустым
  "serial": Text,     // серийник экземпляра (связь между цепями); может быть пустым
  "cost":   Float,    // стоимость приобретения, трудочасов
  "life":   Float,    // расчётный ресурс, часов работы (ёмкость нити переноса)
  "basis":  Text,     // "paid" | "est"
  "src":    Ref?,     // paid: приёмка покупки — стоимость заверена и проверяема
  "origin": Ref?,     // предыдущая запись экземпляра (перевыпуск)
  "note":   Text,     // est: пояснение оценки; может быть пустым
  "lot":    LotLink?, // v3 (ИР-023): звено подниточки своей покупки, которым взят экземпляр
  "repair": Ref?,     // v4 (ИР-015): своя сделка, которой принят и оплачен ремонт — на неё растёт cost
  "days":   Int?      // v5 (ИР-011): календарный срок службы в днях, со дня этой записи
}
```

**Два пути ввода.** `paid` — куплен внутри системы: `src` → `Acceptance` покупки, `cost` обязан совпадать с её стоимостью (проверяемо по ссылке). `est` — существующий инструмент вводится декларацией владельца: стартовая оценка «цена в валюте / средняя часовая ставка» (метод ИР-011), всюду показывается с пометкой «оценка владельца»; дисциплинируется бинарным согласием покупателя продукции — как с эмитентами порций (records.md §12.7).

**Перевыпуск (`origin`) — одна механика на три случая.** Новая запись того же экземпляра со ссылкой на предыдущую; правило признания: **`cost` новой ≤ остаток предыдущей** (её `cost` − `after` последнего звена нити). Случаи: (1) **перепродажа** — перевыпуск в цепи покупателя (`paid`, `src` → приёмка покупки; потолок цены = остаток продавца — учётная остаточная стоимость, economy.md §5б); (2) **переоценка** — перевыпуск в своей цепи, **только вниз**: признание внесистемного износа — самонаказание (владелец режет собственный несобранный остаток), поэтому доверия не требует; вверх — денежный насос, не признаётся; (3) **повторный ввод** после перерыва. Цепочка `origin` — прослеживаемая история экземпляра (вместе с `serial` — между цепями); глобальный инвариант «Σ переноса за жизнь экземпляра ≤ стоимость первого ввода» следует из локальных нитей и правила перевыпуска по индукции. Расчётный ресурс `life` заявляет владелец; ошибся — риск его: ранняя смерть инструмента съедает несобранный остаток, долгожительство даёт бесплатные машино-часы (симметрия рисков, ИР-011).

**Ремонт — единственный путь стоимости вверх (v4, решение участника 2026-09-20, ИР-015).** Правило «`cost` новой ≤ остаток предыдущей» держит стоимость вниз, и это верно для перепродажи, уценки и повторного ввода. Ремонт — исключение, и единственное: вещь чинят чужим трудом, этот труд принят и оплачен, и ровно на него вещь дорожает. Перевыпуск с `repair` — ссылкой на **свою сделку**, которой ремонт принят и оплачен, — поднимает потолок: `cost` новой ≤ остаток предыдущей + уплаченное по этой сделке. Проверяет это агрегатор сам: запись — своя, сделка — своя и состоявшаяся, и **одна сделка оправдывает одно удорожание** (второй перевыпуск на ту же сделку не признаётся). Без `repair` потолок прежний. Перенос из непризнанной записи в продукцию не считается: **сделка по работе с таким переносом не признаётся** (`DealsOnTable::carry_sound`, то же место, где судятся нить труда и звенья партий), в витрине работы это видно полем `carry_sound`, а `bc accept` за такой перенос не платит — иначе стоимость бралась бы из воздуха (ИР-011, аудируемый инвариант). Сам ремонт при этом — обычная работа ремонтника на заказ владельца: его труд идёт в цены осей, а вещь владельца дорожает на оплаченное. CLI: `bc tool add ИМЯ --origin ПРЕЖНЯЯ --repair СДЕЛКА --cost N --life H`.

**Две шкалы износа — износ по большей (v5, решение участника 2026-10-10, ИР-011).** Реальная вещь изнашивается и работой, и временем: машина — пробегом и простоем, печь — моточасами и ржавчиной. Поэтому у записи две шкалы — ресурс `life` и календарный срок `days` (со дня самой записи), — а **износ считается по той, что дала больше**:

```
износ_по_использованию = собрано нитью переноса
износ_по_календарю     = cost × min(1, (now − дата записи) / days)
остаток                = cost − max(двух износов)          ← потолок всего
```

Остаток — это и потолок переноса в одной работе (`records::carry_step` с календарём), и цена перепродажи (economy.md §5б), и потолок перевыпуска (правило выше). Момент, на который считается календарь при переносе, — **конец работы** (`records::labor_interval(wr).second`), а каждое звено нити проверяется потолком **на своё время**: что было законно тогда, остаётся законным, норма не переписывается задним числом.

Два следствия, ради которых это и сделано:

- **Простой перестаёт быть бесплатным.** Печь 300ч с ресурсом 8000 моточасов и сроком 10 лет, простоявшая 3 года при 500 отработанных моточасах: переносом вернулось 18.75ч, остаток по норме — 210ч, и **71.25ч не вернётся никогда**. Отсюда ответ на «зачем давать вещь в работу»: держать её без дела дороже, чем пустить за свои же часы износа (ИР-013).
- **Шкалу безопасно добавлять.** Любая новая шкала остаток только **снижает**, завысить ею цену нельзя — поэтому необязательные шкалы не нужно ограничивать протоколом. Условие одно: у шкалы должен быть календарь или счётчик с подписанными показаниями (`--meter`, records.md §9.4 v8).

**Сменные части — не шкалы, а отдельные записи.** Свечи, шины, масло не втискиваются шкалами в запись машины: машина — композит, у каждой части своя стоимость и свой срок, замена — новая запись плюс списание старой. Это тот же механизм, что печь и мука: каждая часть переносит свою стоимость отдельно. Путать износ вещи с расходом материала не надо.

**Явная переоценка — только для непредсказуемого.** Календарная шкала и есть автоматическая переоценка простоя, отдельный акт для него не нужен. Перевыпуск вниз остаётся для того, чего норма не предскажет: вещь треснула, устарела, появилась модель вдвое быстрее. CLI: `bc tool add ИМЯ --cost N --life H [--days D]`, `bc tool show` печатает оба износа и говорит, какая шкала главная.

### 10.3. ProductionStep (0x62) — Производственный шаг

Одно преобразование: входные ресурсы → труд → выходные ресурсы.

**Заметка v2 (ИР-011):** учёт входов/выходов и переноса стоимости живёт в самом `WorkRecord` (records.md §9.4 `inputs`/`outputs`/`carry`) — весь конвейер приёмки и оплаты смотрит туда. `ProductionStep` оставлен для будущих **многошаговых цепочек** (`ProductionChain`, records.md §10.4); его формат будет пересмотрен при их реализации — возможное дублирование полей с `WorkRecord` признано и отложено.

```
ProductionStep = {
  "t":       0x62,
  "work":    Ref,        // ссылка на WorkRecord
  "loc":     Ref?,       // место (цех, узел сети)
  "inputs":  [{ "resource": Ref, "qty": Float }, ...]?,
  "outputs": [{ "resource": Ref | Text, "qty": Float }, ...]?
}
```

## 11. Экономика (0x70–0x7F)

### 11.1. Transfer (0x70) — Передача трудочасов

Единственный способ обмена ценностью в системе. Часы **именные** (records.md §12.7): каждая порция несёт эмитента — цепь, чей долг её обеспечивает. **Кошельки — по веткам** (economy.md §5а, v0.6): тратящая ветка = ветка, в которую записан блок перевода (её ключ и подписывает трату); получателю кошелёк указывает поле `to_node`. Долг остаётся на уровне цепи — должен человек, из какого бы кармана ни тратил.

```
Transfer = {
  "t":         0x70,
  "from":      Bytes(32),     // UserId отправителя
  "to":        Bytes(32),     // UserId получателя
  "origins":   [{             // именные порции; сумма units = сумма перевода
      "issuer": Bytes(32),    //   эмитент (цепь-должник)
      "units":  Float,        //   количество его часов
      "src":    Ref?,         //   v6: вексель — блок, где эта бумага пришла к плательщику
      "prev":   Ref?          //   v6: прошлая трата этого векселя плательщиком
  }, ...],
  "settles":   Ref?,          // КАКОЕ ОБЕЩАНИЕ закрываю: Pledge (v4, опционально)
  "timestamp": Int,
  "accept":    {...}?,        // v5: ЗА ЧТО плачу — сама приёмка (records.md §9.5)
  "until":     Int?           // v6: срок ответа продавца; у сделки обязателен
}
```

- **Самоэмиссия** (`issuer == from`): рождение новой пары «долг/требование» — плательщик уходит в минус по собственной бумаге (records.md §12.2). Никакого предварительного баланса не требуется.
- **Погашение** (`issuer == to`): бумага вернулась к эмитенту — его долг уменьшается, порция аннигилирует.
- **Передача чужой бумаги**: обычное обращение (индоссамент). Получатель волен отказаться от сделки, если эмитенты порций ему не внушают доверия, — курсов и дисконтов нет, решение бинарное (records.md §12.7); отказ — ответ на оферту (records.md §11.13).

**Transfer v6 — оферта и векселя (решения участника 2026-10-14, economy.md §4.4).** Сделка — **оферта**: часы переходят, только когда продавец принял её записью `DealReply` (records.md §11.13) не позже `until`. Срок выбирает покупатель для каждой сделки; молчание до срока — то же, что отказ. Чужая бумага тратится **по векселям**: порция называет `src` — блок, в котором эта бумага пришла к плательщику (сделка, которой ему заплатили, или его перемещение между ветками), и `prev` — его прошлую трату этого векселя (у первой траты нет). Кодек проверяет при записи и при чтении:

- у сделки (`accept`) `until` обязателен и позже `timestamp`; у перемещения между своими ветками его нет — отвечать некому;
- своя бумага (`issuer == from`) векселя не называет: она рождается в этой записи; чужая — называет обязательно; `prev` без `src` не бывает;
- один вексель — одна порция; порция — положительное число часов.

Остальное — отношения между записями разных блоков, их проверяют читатели по одному правилу (`records/settlement.h`):

- **ответ** (`records::answer_of`): засчитывается первый ответ в цепи продавца, в ветке `to_node` — кошелёк, в который платят, отвечает сам, — данный не позже `until`;
- **вексель** (`records::check_bill`): вексель тратится только из кошелька, куда пришёл; после того как держатель принял сделку-источник; каждая трата называет предыдущую; сумма не больше пришедшего. Оферта, отвергнутая или просроченная к следующей трате, часов не держит; оферта, ждущая ответа, — держит. С первого звена, где нить рвётся, траты — не бумага;
- **сделка двигает часы**, только если она по адресу (как прежде), принята продавцом в срок и обеспечена — каждая порция чужой бумаги лежит на целой нити своего векселя. Иначе она `unsettled`: не двигает ничего и не мешает сделке, которая её заменит (`records::DealClaim::settled`);
- **выкуп по заранее подписанному возврату** (records.md §9.8 v5) ответа не ждёт, если платит бумагой держателя или своей эмиссией адресата (`records::pre_accepted_buyback`) — возврат и есть согласие, данное заранее.

Перемещение между своими ветками — `Transfer` без приёмки из цепи в саму себя: тратит векселя ветки блока и кредитует ветку `to_node`; ответа не требует.

**Transfer v5 — приёмка внутри перевода (решение 2026-09-14, ИР-023).** «За что плачу» — не ссылка на приёмку (`reason`, ключ 5 снят и не переиспользуется), а сама приёмка: поле `accept`. Сделка — одна запись: оценка и её оплата подписаны вместе. Кодек проверяет это при записи и при чтении — запись, нарушающая правила, не существует:

- с `accept`: сумма порций ровно равна `labor_units + carried_units` (records.md §12.8), `to` — цепь принятой работы (`accept.work.chain`) и отпуска (`accept.release`, если назван) — или, при перепродаже (records.md §9.8 v4), цепь отпуска держателя, и тогда в приёмке нет ни труда, ни разбивки по осям; `to ≠ from` — свою работу не принимают;
- без `accept`: только перемещение чужой бумаги из одной своей ветки в другую (`to = from`, economy.md §5а) — часы не уходят в другую цепь без принятого труда (records.md §12.9), своя бумага в себя не ходит.

Отсюда треугольника («платит один, принимает другой») нет по построению: платит тот, кто принимает (records.md §12.9). Почему приёмка внутри перевода, а не оплата внутри приёмки и не новый тип: деньги остаются в одном типе записи, и принцип «`Transfer` — единственный способ обмена ценностью» держится буквально (разбор — ИР-023, пункт 6).

**Сделка не по адресу ничтожна** (records.md §9.5, 2026-09-14). Кому достаётся результат, решает продавец — заказчиком в записи труда (records.md §9.4) или отпуском (records.md §9.8). Адресованность — отношение двух записей в двух цепях, а кодек видит одну; поэтому её проверяют читатели, по одному правилу (`records::addressed_to`): получатель такие часы не принимает (`bc transfer recv`), денежные и статистические витрины агрегатора их не считают — перевод не по адресу не двигает ни бумагу, ни цены.

**Transfer v4 — `settles` (решение 2026-07-13, ИР-006).** У перевода было **одно** поле основания, а нужно оно двум разным вопросам: *за что плачу* и *какое обещание этим закрываю*. Погашение `Pledge` засчитывалось, когда `reason` указывал на обещание, — но records.md §12.9 требует, чтобы `reason` указывал на **приёмку**, иначе перевод не признаётся. Одновременно одно поле это не выражало, и обещание, честно оплаченное трудом, навсегда оставалось «активным» и протухало.

Поэтому вопросы разведены по разным полям:

- «за что плачу» — **приёмка** (до v5 — ссылкой `reason` → `Acceptance`, с v5 — самой приёмкой в поле `accept`). Обязательно (records.md §12.9).
- `settles` → **`Pledge`**: какое обещание этим закрывается. Опционален — прямая сделка без обещания его не несёт.

Погашение обещания считается **только** по `settles`. Прежний путь (`reason` → `Pledge`) отменён: он противоречил records.md §12.9 и был мёртвым.

**Transfer v3 — реализовано (2026-07-11):** `reason` обязателен — перевод без основания не признаётся и отклоняется при приёме (строгая эквивалентность, economy.md §4.2, records.md §12.9); выплаты не превышают `labor_units` приёмки, а в статистику ставок входят только **точно** рассчитанные сделки (records.md §12.8 «=», records.md §11.2). Самоэмитирующий перевод несёт звено **нити эмиссии** (economy.md §4.3) — опциональную группу полей:

```
  "emission": {               // присутствует ⇔ есть порция issuer == from
    "seq":        Int,        //   сквозной счётчик звеньев цепи
    "prev":       Ref?,       //   предыдущее звено (у первого отсутствует)
    "debt_after": Float       //   декларируемый долг после операции
  }
```

Самоэмиссия без звена нити отклоняется при приёме. Погашение нанизывается на ту же нить квитанцией `Redemption` (records.md §11.5). CLI ведёт нить автоматически (`bc accept`, `bc transfer recv`, `bc wallet`).

### 11.2. DailyAggregate (0x71) — суточные цены осей

Запись в **собственной цепи агрегатора** (автор блока и есть агрегатор — отдельное поле не нужно; подпись, история и перепроверяемость бесплатны). Клиент при нескольких агрегаторах берёт медиану (устойчива к одиночному вранью); действует последняя запись за дату от данного агрегатора (records.md §14.5).

**v5 (ИР-022 шаг 11): цены осей, а не ставки специальностей.** Сделка расписывает свою цену по осям (`records.md §9.5` v4), поэтому сеть публикует, сколько платит за час работы, назвавшей каждую ось, — а цена работы по умолчанию есть сумма цен её осей × часы × k (`economy.md §2а`). Специальность была ярлыком, который человек выбирал из списка; ось — то, что сказала сама сделка. Ключ строки — полный путь оси (`BlockPath`, `records.md §4`).

```
DailyAggregate = {
  "t":         0x71,
  "date":      Int,                // начало суток UTC (ts − ts mod 86400)
  "timestamp": Int,
  "W":         Float,              // economy.md §2б: средняя бумага на трудочас дня =
                                   //   Σ price·hours по осям / Σ часов сделок дня; клиент
                                   //   делит price/W, чтобы средний трудочас = 1
  "indep":     Text,               // ИР-021: параметры взвешивания по независимости
                                   //   контрагентов («v3;ref=axis_prices;window_days=365;
                                   //   max_cycle=4;…») — свидетель пересчитывает по той
                                   //   же методике, а не гадает, какая была
  "axes": [{                       // v5; ключ 2 (ставки специальностей) снят
    "axis":  BlockPath,            // определение оси (AxisDef, records.md §11.12)
    "price": Float,                // СЫРАЯ стч за час работы, назвавшей ось, после
                                   //   сглаживания (нормированная = price/W)
    "hours": Float,                // Σ hours_raw сделок дня, назвавших ось, СЫРЫЕ
    "deals": Int,                  // число таких сделок
    "weighted_hours": Float        // ИР-021: Σ вес·hours_raw — объём, переживший
                                   //   взвешивание; доверие = weighted_hours/hours
  }, ...]
}
```

Семантика вычисления (economy.md §8.2): агрегат с датой D считается по сделкам **предыдущих суток** (D−86400…D) — «коэффициенты этого дня — из сделок вчерашнего»; входят только **рассчитанные** сделки (оплата ровно `labor_units + carried_units`), не самосделки, чья работа на месте и чья разбивка сходится с ценой. По каждой оси `цена_дня = Σ стч на оси / Σ часов работ, назвавших ось` — час сделки входит в каждую её ось, а её стч на оси — только в эту ось; сглаживание `price = α·цена_дня + (1−α)·вчерашняя` (α = 0.3); при объёме ниже порога цена наследуется, а у новой оси без свидетельств цены нет вовсе — приора нет и быть не должно: за неё ещё никто не платил. `W = Σ price·hours / Σ часов сделок дня`: сумма по осям сходится с тем, что сделки заплатили, и делится на часы, которые они на самом деле заняли; ось, слишком тонкая для цены, в `W` не входит.

**v2 (ИР-011):** «рассчитанная» сделка — оплата ровно `labor_units + carried_units` (records.md §9.5); в усреднение по-прежнему входит **только** `labor_units` — перенос стоимости средств производства не искажает цену живого труда.

**v4 (ИР-021): вес сделки по независимости контрагентов.** Исключения самосделок мало: пара A↔B (и тем более кольцо A→B→C→A) может накручивать `k`, двигая сетевые цены того, что они называют, — завышать часы дорого (свидетели, непересекающиеся слоты economy.md §3), а `k` бесплатен. Поэтому вклад сделки в усреднение множится на вес `1 − R·excess`, где `R` — доля потока ребра «плательщик→работник», возвращающаяся по циклу длины ≤ `max_cycle` за окно, а `excess` — превышение цены часа над сетевой ценой того, что сделка назвала. Дисконт требует **обоих** условий: честная деревня взаимна, но торгует по обычной цене, а дорогая односторонняя сделка — законная премия. Опора — **среднее арифметическое по сделкам** (ратифицировано 2026-09-08: «усреднённый трудочас» и есть среднее арифметическое), с 2026-09-11 — не по корзине специальности, а по каждой названной оси (см. «Опора ИР-021 — сетевые цены осей» ниже). Сделки **не** схлопываются по рёбрам — если большинство честно, каждая сделка есть настоящий труд и обязана считаться, даже когда двое работают только друг с другом.

Чем за это платим, замерено: пара, торгующая по цене ×1.3 и наращивающая **число** сделок, при опоре по рёбрам оставалась видна всегда (аномалия 1.28× при любой доле), а при среднем по сделкам аномалия сползает 1.28 → 1.21 (28% сделок) → 1.16 (43%) → 1.11 (61%) → 1.07 (75%). Дисконт при этом не исчезает совсем — его удерживает нижний зажим `kappa_min` — но слабеет: при 86% сделок пары уцелевает ≈82% её объёма против ≈8% на незалитой оси. Цена принята сознательно: заливать ось значит заявлять **часы**, а часы дороги (`economy.md §3`), и кругооборотная половина конъюнкции продолжает работать — заливающая пара взаимна по построению. Среднее к тому же спускается плавно, без обрыва на 50%, который был бы у медианы по сделкам. Сделка, ни одна ось которой ещё не оценена, не судится вовсе. Коэффициент сглаживания множится на **доверие ко дню** = `Σweighted_hours / Σhours`: день, почти весь ушедший в дисконт, оставляет вчерашнюю цену почти нетронутой. `hours` и `deals` остаются сырыми — труд был, под вопросом его оценка. Параметры методики публикуются в `indep`.

**От ставок специальностей к ценам осей (ИР-022, 2026-09-10 → 11).** Сначала из ключа ставки ушёл разряд (RateEntry v3): час мастера выходил дороже по одному званию, сверх того, за что платила сама сделка. Затем ушла и специальность (v5): ставки специальностей заменены ценами осей, записи `Specialty`/`Grade` сняты (records.md §9.1, records.md §9.2). Прежние раскладки не читаются: обратной совместимости нет (решение участника 2026-09-11) — читатель, наполовину понимающий старый агрегат, хуже того, что честно говорит «не могу».

**Опора ИР-021 — сетевые цены осей (вариант «б», выбран участником 2026-09-11).** Без разряда в ключе корзина специальности смешала мастеров с учениками, и честный мастер в деревне стал подозреваемым. Опора теперь та же, что у карты ренты (`records.md §11.11`): у каждой оси — Σ стч на ней / Σ часов работ, которые её назвали, по всем рассчитанным сделкам окна; ожидаемая цена сделки — сумма по названным осям. Надбавка, названная в разбивке, оценена всеми, кто эту ось называет, и аномалией не является. Цена оси считается, только когда её назвали хотя бы `min_axis_payers` (4) разных плательщика: ось стоит столько, сколько за неё платят независимые люди, — иначе пара завела бы ось только для себя и оценила бы ею собственное завышение. Порог аномалии калибруется по разбросу всей сети. Сделка, чья разбивка не сходится с ценой, в ставку не входит вовсе — как и в книгу осей.

Дисконт режет не оплату — работник получает всё, о чём договорился, — а вес сделки в средней.

### 11.3. Pledge (0x72) — Обещание финансирования

Публичное обещание оплатить (часть) стоимости будущей работы (economy.md §7). Само по себе ничего не передаёт — вес имеет только расчёт: `Transfer` с `reason` → на этот Pledge. Отзывен до расчёта (records.md §11.4), авто-истекает по `expires`.

```
Pledge = {
  "t":         0x72,
  "target":    Ref,           // финансируемая работа/идея (Concept, Composite, WorkRecord, ...)
  "units":     Float,         // обещанные усреднённые трудочасы
  "executor":  Bytes(32)?,    // опционально: конкретная цепь-исполнитель
  "expires":   Int?,          // Unix timestamp; после — считается отозванным
  "timestamp": Int
}
```

Правила расчёта:

- **Частями**: несколько сделок (переводов с приёмкой внутри, records.md §11.1 v5) с `settles` → Pledge, по мере приёмки этапов — постепенное выполнение, поэтапная оплата.
- **Ровно стоимость** (2026-07-10, было «не выше»): сумма всех выплат по одной работе равна сумме `labor_units` её приёмок — последний транш закрывает остаток ровно (records.md §12.8). Превышение обещанного над стоимостью — сигнал приоритета, не цены: не выплачивается.
- **Детерминированное истечение**: расчётом считается только `Transfer` с `timestamp` < `expires`. Сравниваются два значения из цепей — гонок стенных часов нет. Порядок «отзыв против расчёта» упорядочивается через `timestamp_witnessed` (sync.md §9).

### 11.5. Redemption (0x74) — Квитанция погашения

Звено нити эмиссии со знаком «+» (economy.md §4.3): эмитент, получив собственную бумагу, фиксирует уменьшение долга. Пишется автоматически при приёме перевода со своей бумагой (`bc transfer recv`). Кредитная история цепи — максимальный закрытый долг, скорость погашения (economy.md §5а) — читается прямо по нити.

```
Redemption = {
  "t":          0x74,
  "transfer":   Ref,          // Transfer плательщика, вернувший бумагу
  "units":      Float,        // сколько своей бумаги аннигилировало
  "seq":        Int,          // сквозной счётчик звеньев (общий с эмиссиями)
  "prev":       Ref?,         // предыдущее звено нити
  "debt_after": Float,        // декларируемый долг после погашения
  "timestamp":  Int
}
```

Два звена с одним `seq` — эквивокация, объективное доказательство (кандидат `FraudClaim`, вскрывается при встрече ветвей). Чекпойнт `(seq, долг)` в коммите публичной вершины и правило «незасвидетельствованная эмиссия — без веса» — после реализации коммитов вершины (economy.md §4.3).

**v2 — сторно (2026-10-14, economy.md §4.4).** Квитанция, чей `transfer` называет **собственную** сделку эмитента, — сторно: продавец эту оферту отверг или пропустил её срок, и своя бумага, объявленная звеном самоэмиссии, не родилась. Формат прежний; что это сторно, видно из ссылки (`records::is_reversal`). Объявленный долг возвращается на `units`. Сторно — не погашение: кредитная история не считает ни его, ни отменённую им эмиссию (records.md §11.6). Пишет его клиент покупателя, узнав от агрегатора, что оферта отвергнута или просрочена (`bc transfer status`). Сторно сделки, которую продавец на деле принял, — объявленный прочь долг; две подписи противоречат друг другу, и агрегатор показывает это в следе (`false_reversals`).

### 11.7. WorkCloud (0x75) — облако образцов работ (ИР-018 → ИР-022)

Подписанная запись в цепи агрегатора — близнец `DailyAggregate` для геометрии работ (`specialty-axes.md §10`). Прежнее имя — `SpecialtyCloud`; номер тот же, раскладка новая (v4), обратной совместимости нет.

**Точка — образец работы (v4, ИР-022 шаг 11).** Образец — приёмка, которую другие сделки назвали в `like` (`records.md §9.5`): «такая же работа, как та». Его семья — он сам и все рассчитанные сделки, назвавшие его прямо или через другую сделку, которая его назвала. «Профессия» перестаёт быть строкой справочника: это описание работы, которое люди раз за разом повторяют, и облако показывает те, что прижились. Образец, который никто не повторил, — просто сделка, а не точка: семья меньше двух сделок в облако не входит.

**Место образца — из чего сложилась цена его семьи:** доля всего уплаченного, пришедшаяся на каждую ось разбивки, и доля перенесённых средств производства (суммы по семье, делённые на всё уплаченное). Сделки те же, что у книги осей (`records.md §11.11`). Близость — Σ√(aⱼ·bⱼ) по долям: 1 — тот же состав, 0 — ничего общего, и тогда это не сосед вовсе. Ни у одной оси нет веса. Доли, а не цена часа: ставка — высота над картой, а не её координата (`specialty-axes.md §7`).

**Машинной роли у облака больше нет.** Приор ставки тонкой специальности ушёл вместе со ставками специальностей: новое сочетание оценённых осей оценивается их суммой (`records.md §11.2`), а у новой оси цены нет, пока за неё не заплатят. Облако — карта для людей: какие описания работ лежат рядом.

```
WorkCloud = {
  "t":        0x75,
  "date":     Int,                 // начало суток UTC
  "snapshot": Bytes(32),           // хеш входа: набор блоков
  "params":   Text,                // "v4;basis=samples;affinity=bhattacharyya;k=5;min_family=2"
  "sources":  [Bytes(32), ...],    // цепи-источники (пилот: цепь самого агрегатора)
  "points":   [{
    "sample":    Ref,              // приёмка-образец
    "title":     Text,             // название его работы — вольный текст, для людей
    "deals":     Int,              // размер семьи
    "neighbors": [{"sample": Ref, "weight": Float}, ...]  // k ближайших, вес 0..1
  }, ...],
  "timestamp": Int
}
```

Витрина — `GET /economy/cloud` (`?coords=1` — спектральные координаты для картинки), CLI `bc cloud`. Самого образца может и не быть у агрегатора: семья вокруг ссылки собирается всё равно.

### 11.8. AxisAttestation (0x76) — снята (2026-09-10)

Запись заверяла значение объявленной оси деятельности («у учителя опасность 0.02»): агрегатор брал взвешенную по разряду медиану практиков (ИР-019), а с v2 — и заявления сторон рассчитанной сделки, дельтой к профилю каталога (ИР-020). **Снята, потому что у её значений — `x` — не осталось читателя.** Читателей было два: план регрессии цен осей (снята, `records.md §11.9`) и геометрия облака (с v3 читается из разбивок сделок, `records.md §11.7`). Номер `0x76` не переиспользуется; раздел оставлен, чтобы старые ссылки не ломались.

И по сути: когда сделка сама расписала, за что заплачено (`records.md §9.5` v4), объявленное «сколько опасности в часе такой работы» — второй ответ на тот же вопрос, причём бесплатный. Подписанная цена со своей разбивкой говорит то же самое дороже.

Что из этого стоит помнить (подробно — ИР-019 и ИР-020 в `dev-ideas.md`): голос — это цепь, **подписавшая блок**, а не поле внутри записи (пустое поле схлопывало всех в один голос); сторону сделки нужно **выводить** из самой сделки, а не объявлять; строку, написанную для людей, протокол не должен читать никогда.

### 11.9. AxisPrices (0x77) — снята (ИР-020 закрыта, 2026-09-10)

Запись публиковала гедонистическое разложение ставок: цены осей, выведенные регрессией из рассчитанных сделок, протокол экзамена допуска осей и разброс цен по скользящему контролю. **Снята вместе с регрессией.** Номер `0x77` не переиспользуется; раздел оставлен, чтобы старые ссылки не ломались.

**Почему снята — по измерению, а не по решению.** С тех пор как сделка расписывает свою цену по осям (`records.md §9.5` v4), цена оси **читается**, а не выводится (`records.md §11.11`). У регрессии оставалась одна роль, не отменённая участником: опора карты ренты, отличающая канал (переплачивает один) от дефицита (дороже платят все). Замер на прогоне года с внедрёнными каналом и дефицитом, эффективное число плательщиков превышения:

| опора | честно | канал | дефицит |
|---|---|---|---|
| регрессия по профилям `x` | 13.6 | 1.3 | 14.0 |
| книга осей | 10.7 | **1.1** | 14.0 |

Книга осей различает их так же, а канал — даже чище. Прочие роли регрессии отпали решениями участника раньше: подсказка ставки для никогда не торговавшейся работы («пусть договариваются с нуля»), экзамен допуска осей (базис больше не выбирается — ось заводит тот, кто её использует, `records.md §11.12`), вытеснение разряда (его вытесняет сама разбивка по осям).

И довод «регрессия — ревизор, потому что не читает объявленное» оказался **неверным**: план регрессии строился из профилей `x`, а они тоже объявляются. Без `x` она не работает вовсе, поэтому решение про `x` принимается вместе с ней.

Карта ренты перенесена на книгу осей: `/economy/axis-ledger?rent=1`.

### 11.10. DealProfile (0x78) — снята (2026-09-10)

Запись описывала одну выполненную работу: сначала разбивку её цены по осям, потом — когда разбивка переехала в саму приёмку (`records.md §9.5` v4) — только необязательную интенсивность осей (`x`), пояснение и шаблон для переиспользования. **Снята, потому что у неё не осталось читателя**: интенсивность работы шла лишь в план регрессии, а регрессия снята (`records.md §11.9`). Денег запись не несла, в книгу осей не входила; держать тип без читателя значило бы оставить рядом с живой дорогой описания работы вторую, мёртвую. Номер `0x78` не переиспользуется.

Цена одной работы, расписанная по осям, — в приёмке (`records.md §9.5` v4). Повторять разбивку для однотипных работ удобно на стороне клиента (`bc accept --axis-share`), протокольный шаблон для этого не нужен.

### 11.12. AxisDef (0x79) — ось, заведённая в цепи (ИР-022)

Словарь труда перестал быть файлом, который возит с собой агрегатор. Раньше тот, кто правил файл, решал, какие грани труда существуют, — последняя централизующая точка в оценке труда, после того как **значения** стали делом практиков (ИР-019; позже ушли и они — `records.md §11.8`), а **цены** — делом сделок (`records.md §9.5` v4). Теперь ось — обычная запись: заводит кто угодно, ссылается кто угодно, сила у неё **от употребления**, а не от чьего-то благословения.

```
AxisDef = {
  "t":     0x79,
  "slug":  Text,           // ключ, по которому на неё ссылаются
  "ru":    Text,           // название
  "description": Text,     // АРГУМЕНТ: что значит, почему одна ось, чем не является
  "ts":    Int,
  "parent":  Ref?,         // более широкая ось / семейство
  "same_as": Ref?          // заявка на слияние; автоматически не применяется
}
```

**Аргумент — это и есть суть.** Завести ось не мешает никто, поэтому хорошую от плохой отличает только то, насколько она обоснована: что она значит, почему это **одна** ось, а не две, и чем она **не** является. Ось, которой пользуются снова и снова, ничего про неё не написав, видна как таковая (`described: false` в книге осей) — и эта видимость есть всё принуждение, какое тут есть. `AxisDef` с пустым `description` определением не считается: заявить слаг — не значит объяснить ось.

Оси «прочее» в протоколе нет **намеренно**: чего не можешь назвать — назови.

**`same_as` — заявка на слияние, а не слияние.** «Эта ось и та — одно и то же». Опубликовать её волен любой: автор первоисточника, а если он умер или потерял ключи — кто угодно. Заявки не применяются автоматически и взвешиваются тем же, чем взвешивается тут всё, — употреблением. Агрегатор вправе показывать подозрение, но не сливать сам: прибор, не судья.

**Спор о слаге — факт о слаге.** Два определения одного слага из разных цепей не «разрешаются»: для показа берётся первое по (времени, цепи), а расхождение остаётся видимым.

CLI: `bc axis-define --slug danger --ru "Опасность" --description "..."`. Пилотная цепь из 23 осей словаря (`specialty-axes.md §4`) заводится `docs/pilot/seed-axes.sh` — это **не привилегированный источник**, а одна цепь среди прочих, просто чтобы пилоту было с чего начать.

### 11.11. Книга осей — куда труд сети ушёл на самом деле (ИР-022)

Не запись, а витрина: `GET /economy/axis-ledger`, CLI `bc axis-ledger`. Складывает разбивки рассчитанных сделок (`records.md §9.5` v4) и ничего не выводит.

| поле | что это |
|---|---|
| `units` | Σ трудочасов, ушедших на эту ось |
| `hours` | Σ часов работ, которые её назвали |
| `share` | `units` / Σ`units` — **доля всей оплаченной сети**, ушедшая на ось |
| `per_hour` | `units` / `hours` — сколько стч за час такой работы |
| `spread` | разброс `units/hours` по сделкам, взвешенный часами |
| `deals`, `chains` | сколько сделок и сколько **разных цепей** её назвали |
| `described` | есть ли у оси определение в каталоге осей |

**`share` — факт, а не оценка.** Цена оси нигде не назначается и ниоткуда не выводится: сеть говорит только, сколько труда через ось прошло.

**Широкий `spread` не значит «модель плоха»** — модели тут нет. Он значит, что **сеть не согласна, что это одна ось**: за одно и то же платят по-разному. Это сигнал ось **разделить**, и он приходит прямо из сказанного людьми, без выбрасывания наблюдений и без подгонки.

**`chains`, а не только `deals`.** Одна оживлённая пара — это свидетельство одного голоса, сколько бы сделок она ни провела.

**Карта ренты — там же, `?rent=1`, по работникам (ИР-022 шаг 11).** Опора — не модель, а сетевая цена часа каждой названной оси, прочитанная из тех же сделок: ожидаемая цена = Σ `per_hour` названных осей. Строка — работник (с вольным названием его последней работы, для людей) и несёт `fact`, `expected`, `resid`, `periods_over/periods_seen` и `rent_payers` — сколько плательщиков на самом деле платят превышение. Канал — это ровно «один плательщик переплачивает одному работнику», поэтому работник — то место, где он виден; дефицит виден дважды — ростом цены оси день ото дня и рентой, которую работнику платят все. Опора берётся **по всей сети**, а не по самому работнику: иначе тот, кому дороже платят все, был бы сам себе опорой, и дефицит растворился бы. Сводного балла нет по той же причине, что в `records.md §11.6`.

**`described: false` — не ошибка.** Заводить оси волен каждый; это видимость того, что осью пользуются **без аргумента**. Чем чаще такую ось переиспользуют, тем громче сигнал: либо опишите, либо это не ось.

### 11.6. Кредитная история с нити эмиссии — слой 1 экономического следа (ИР-010)

**Реализовано (2026-07-16).** Первая витрина экономического следа: что нить эмиссии (records.md §11.1, records.md §11.5, economy.md §4.3) говорит о цепи **до** какого-либо доверия третьим лицам. Чистая функция `records::credit_history` (заголовок `records/credit.h`), потребитель — `bc trust <цепь|префикс>`.

**Считается только локально** (решение ИР-010 п. 3): звенья читаются из блоков цепи-предмета, которые спрашивающий уже держит у себя (собственные ветки — для своей цепи, `external_blocks` после слияний — для чужой). Никакого агрегатора: это личная, никем не опосредованная картина.

Метрики (все — по видимой части нити):

- **выпущено / погашено** — суммы самоэмиссий и погашений (и доля `redeemed/issued`);
- **пик долга** — самый глубокий задекларированный `debt_after`;
- **максимально возвращено с пика** («столько доверили — вернул») — наибольшее снижение долга от пика за историю (максимальная просадка кривой долга);
- **объявленный долг сейчас** — `−debt_after` последнего видимого звена;
- давность последнего погашения и последней самоэмиссии;
- **сторно** (records.md §11.5 v2): сколько оферт отвергнуто или просрочено и на сколько часов. Ни выпущенным, ни погашенным это не считается, а кривая долга (пик, «столько доверили — вернул») идёт так, будто отменённой эмиссии не было: иначе отказ друга выдавался бы за возвращённый долг.

Правила честности (обязательные):

1. **Неполная картина — не порок цепи, а свойство наблюдателя.** Видимые звенья считаются против `max(seq)+1`; при пропусках выводится «видно N из M — картина неполная», и **осуждающие флаги не поднимаются** (пропущенным звеном могло быть погашение).
2. **Флаг «долг растёт без погашений»** — только на полной картине: ≥2 самоэмиссий и ни одного погашения.
3. **Флаг «нить не сходится»** — только на полной картине: задекларированный долг ≠ выпущено − погашено (самоаттестация нарушена).
4. **Эквивокация** — одно `seq` в двух разных блоках — сообщается всегда: это объективное доказательство, не зависящее от полноты картины. Один и тот же блок, пришедший дважды (merge + fetch), эквивокацией не является.
5. Рядом с выводом — **цена подделки** источника (подделка нити = эквивокация, ловится при первом расхождении).

### 11.13. DealReply (0x7A) — Ответ продавца на сделку

**Реализовано (2026-10-14, решения участника, economy.md §4.4).** Сделка покупателя — оферта (records.md §11.1 v6); ответ на неё — эта запись в цепи продавца.

```
DealReply = {
  "t":         0x7A,
  "deal":      Ref,       // сделка покупателя: Transfer с приёмкой
  "accepted":  Bool,      // true — принял, false — отказ
  "note":      Text,      // причина; может быть пустой
  "timestamp": Int
}
```

Правила (`records::answer_of`):

- **Отвечает кошелёк, в который платят:** засчитывается только запись цепи продавца (`deal.to`) в ветке `deal.to_node`. Принятые часы — бумага этой ветки, тратить их может только её ключ (economy.md §5а), поэтому и ответ — его.
- **Первое слово окончательно:** засчитывается первый ответ в этой ветке; ветка линейна, «первое» не требует часов. Передумать после принятия нельзя: на принятые часы продавец уже может опереться и тратить их.
- **После срока слово ничего не отвечает:** ответ позже `deal.until` не засчитывается; оферта мертва, часы у покупателя. **Время ответа — не раньше своей ветки** (2026-10-15, economy.md §8.14): больший из его `timestamp` и самого позднего времени, заявленного веткой до него (`ObservedReply::since`; время ветки монотонно, blockchain.md §9.4). Согласие задним числом за блоком, датированным позже срока, — поздно. Насколько твёрдо доказана просрочка, когда ответа нет, — по слияниям (blockchain.md §5.2); степени — economy.md §4.4.
- **Отказ — та же запись** с `accepted = false` и причиной: и согласие, и отказ равно остаются в истории подписавшего.
- Принятие — момент, с которого бумага у продавца: тратить её он может только **после** своего ответа в той же ветке (records.md §11.1 v6, вексель).

Ответ на свою же сделку не пишется (самоприёмки нет — records.md §11.1). Перемещению между своими ветками ответ не нужен.

## 12. Принципы трудовой экономики

### 12.1. Единственная единица ценности

Единственная единица ценности — усреднённый трудочас (`labor_units`). Никакой другой валюты нет.

### 12.2. Трудочасы рождаются взаимным кредитом

Трудочасы рождаются взаимным кредитом (вексельная модель). Пара «долг/требование» возникает в момент оплаты — `Transfer` с самоэмиссией (records.md §11.1): плательщик уходит в минус по собственной бумаге, получатель держит его именные часы. Эмитента-центра и эмиссии нет; система стартует со всеобщего нуля. `Acceptance` определяет **стоимость** работы, но часов не создаёт; до подтверждения получения и проверки качества работа не имеет стоимости.

### 12.3. Природные ресурсы и энергия

Природные ресурсы и энергия не имеют собственной стоимости. Стоимость появляется только через труд по добыче, транспортировке и преобразованию.

### 12.4. Отрицательный труд

Отрицательный труд — умышленное уничтожение принятой продукции. Оформляется через `NegativeWorkRecord`. Уменьшает суммарные трудочасы в системе.

### 12.5. Цены осей

Цены осей ежесуточно рассчитываются агрегаторами по рассчитанным сделкам (records.md §11.2 v5); нормировщик `W` держит средний трудочас на единице (economy.md §2б). Финальное значение — медиана по участвующим агрегаторам. До ИР-022 шаг 11 здесь были коэффициенты пар (Specialty, Grade).

### 12.6. Все обмены

Все обмены — только через `Transfer` в усреднённых трудочасах. С v5 (ИР-023) «за что» — приёмка — едет внутри этого же перевода (records.md §9.5).

### 12.7. Именные часы, никакой социализации

Именные часы, никакой социализации. Часы разных эмитентов не смешиваются: каждая порция несёт цепь-должника (records.md §11.1 `origins`), а чужая бумага — ещё и свой вексель, блок, где она пришла к плательщику (records.md §11.1 v6), так что происхождение любого часа возводится по блокам к самоэмиссии, где он родился. Единица неизменна — час равен часу, курсов и дисконтов между бумагами нет; контрагент либо принимает бумагу данного эмитента, либо отказывает. Возврат бумаги эмитенту гасит его долг. Смерть цепи — потеря держателей именно её бумаги, а не всех: инфляция единицы невозможна по построению. Инвариант по каждой цепи: её долг равен сумме её часов на руках у других — проверяется аналитически по цепям.

### 12.8. Оплата труда ровно равна его стоимости

Оплата труда ровно равна его стоимости (2026-07-10, было «не выше»). Выплаты по работе в сумме равны `labor_units` её приёмок: сверх труда ничего не рождается, премий нет, а недоплата исключена как скрытая скидка мимо статистики — самоэмиссия снимает ограничение ликвидности, «не могу заплатить» не существует. Вся гибкость цены — k и разряд **до** приёмки, согласуемые на каждый этап отдельно (economy.md §2а, economy.md §4.2). Нужность выражается **приоритетом** (объём обещаний Pledge, economy.md §7); срочность, опасность, вредность — будущие **измерения труда** через специальности и разряды с собственными коэффициентами (records.md §14.8), а не надбавки к цене.

### 12.9. Беспричинных переводов не существует

Беспричинных переводов не существует (2026-07-10). Перевод признаётся только против принятого труда — живого или овеществлённого; с v5 (2026-09-14, ИР-023) приёмка едет внутри самого перевода, и перевод другой цепи без неё не запишет кодек (records.md §11.1). Дарений, кредита «просто так» и прощения долга нет. **Треугольника нет (решение 2026-09-14):** платит тот, кто принимает, — по построению. Уход за нетрудоспособным покупает и принимает тот, кто платит (сын принимает уход на себя, сиделка ухаживает за матерью вне блокчейна); финансирование идей — каждый финансирующий принимает и оплачивает свою работу (economy.md §4.2, economy.md §7). Так закрыт путь коррупционного подарка: оплатить кому-то услугу в цепи нельзя.

### 12.10. Долг гасится только трудом

Долг гасится только трудом. Погашение (`issuer == to`) признаётся только против приёмки труда эмитента — живого или овеществлённого его вещью по остаточной стоимости (economy.md §5б). Закрывает лазейку «скупить бумагу должника и подарить назад».

### 12.11. Заверенность — сигнал, а не пропуск — РЕШЕНО (2026-09-22, форма пломбы — 2026-10-10)

Сделка входит в усреднение и кредитную историю **без всяких пломб**: у одиночного труда свидетелей чаще всего нет, и правило-ворота выбивало бы из измерения именно честную работу (решение участника, economy.md §4.2). Пломбы посторонних цепей на `WorkRecord` остаются сигналом: след цепи показывает отдельно часы принятого труда, заверенные посторонними (`labor_sealed`, `GET /footprint/<цепь>`, строка в `bc trust`), и часы со слов сторон. Ни работник, ни плательщик свидетелями не считаются: первый заверял бы себя, у второго подпись и так стоит в приёмке.

**Пломба — запись в ветке свидетеля** (решение участника 2026-10-10, `records.md §8.9`, `blockchain.md §7.4` v2). Поэтому в следе считаются **цепи, а не ключи** (`attesters`, `attester_chains`): чья пломба — говорит адрес блока, и привязывать ключ к цепи больше не нужно. Отсюда же вторая половина сигнала, которой раньше не было вовсе: **`vouched_hours`/`vouched_works` — сколько чужого труда заверила сама эта цепь.** Ложная пломба теперь стоит свидетелю его собственной истории: она лежит в его ветке рядом со всем, что он о себе утверждает, и бьёт по нему, когда заверенная запись разваливается — часы пересеклись, звено нити битое, вещи никто не видел. Себя не заверяют (`records.md §8.9`).

Было (2026-09-22 … 2026-10-10): пломбы лежали в складе агрегатора непрозрачными байтами; агрегатор проверял подпись, но не знал хозяина ключа, поэтому считались **разные ключи**, а привести ключ к цепи должен был клиент читателя по путям ключей (`blockchain.md §7.5`). Число надувалось в одиночку — ключей заводят сколько угодно. Пути ключей остались нужны там, где подпись приходит без блока: со-подписи слияний и подписи над хешем черновика.

Было (до 2026-09-22): сделка не расчётная без пломб независимых цепей; N свидетелей — открытый вопрос.

## 13. Роль агрегаторов

Агрегатор — узел, который индексирует множество цепочек и публикует производные данные в своём блокчейне. Агрегатором может быть любой пользователь в той мере, в которой позволяют его ресурсы.

**Что вычисляет агрегатор:**

- **Реакции:** суммирует `Reaction.value` по всем копиям одного оригинала (оригинал идентифицируется по `Copy.source`). Учитывает только последнюю реакцию каждого пользователя на данный `target` (по порядковому индексу блока, не по `timestamp_claimed`).
- **Коэффициенты:** ежесуточно собирает все `WorkRecord` и сделки (переводы с приёмкой внутри), вычисляет `DailyAggregate`.
- **Индекс ссылок:** хранит таблицу `(chain, hash) → location`, позволяя находить блоки без прямого обращения к владельцу.
- **Только подписанное своей веткой (sync.md §10.10, 2026-10-17):** блок принимается, только если его подписал ключ его ветки — по пути ключа, сменам ключа и заменам из отзывов; без пути ветки — ответ 428, и клиент выкладывает путь сам; чужая подпись — 403. Читатель проверяет каждый блок снова.
- **Сделки и их адреса (records.md §9.5):** сверяет каждую сделку с записями продавца — заказчиком в записи труда и отпусками (records.md §9.8) — по тому же правилу, что клиент (`records::addressed_to`, `records::recognize_deals`); ничтожные сделки не видят ни денежные, ни статистические витрины. `GET /deals` — сделки по потребностям, `GET /work/<цепь>/<хеш>` — один результат: заказчик, отпуски и сделки со статусом (признана, повтор, двойная продажа, не по адресу), состояние в нити труда (`thread_state`).
- **Оферты и векселя (records.md §11.1 v6, records.md §11.13):** сделка признаётся, только если продавец принял её в срок и каждая порция чужой бумаги лежит на целой нити своего векселя; иначе она не двигает ничего (`unsettled`). `GET /deal/<цепь>/<хеш>` — одна сделка: срок, засчитанный ответ с причиной, статус (`pending`/`accepted`/`refused`/`expired`), обеспечена ли и каждая порция с векселем (сколько пришло, сколько осталось, где порвана нить); для порции чужой бумаги — ещё и то, что продавцу нужно для проверки помимо блоков: положение сделки-источника (`src_standing`), ответ плательщика на неё (`src_reply`) и чем кончились его прежние траты этого векселя (`thread`). Так вся проверка оферты обходится одним запросом; блоки клиент по-прежнему проверяет сам. Стол сделок агрегатор пересчитывает, только когда в хранилище появились новые блоки (`aggregator::deals_on_table`), а каждый блок разбирает один раз (`aggregator::seen_block`): блоки не меняются, и повторный разбор всего хранилища на каждый запрос был главной ценой. `GET /inbox/<цепь>` — оферты, ждущие ответа этой цепи. В `GET /work/<цепь>/<хеш>` у сделок появились состояния `pending`, `refused`, `expired`, `unbacked`. У каждой порции `GET /deal` — долг эмитента при рождении (`birth`: пары «долг, часы», и `birth_unknown`): агрегатор проходит вексель назад до самоэмиссии (`DealsOnTable::births`, economy.md §4.4); `GET /bill/<держатель>/<цепь>/<хеш>/<эмитент>` — то же для одного векселя, с остатком. Время ответа агрегатор считает по ветке (`since`, records.md §11.13), подтверждённое время — по парам встречных блоков слияния (`DealsOnTable::witnessed`, blockchain.md §5.2); у оферты без ответа — степень доказанности просрочки `lapse`: `witnessed` (точку кошелька за сроком закрепило слияние), `seen` (кошелёк ушёл за срок без ответа и до этой точки весь на столе), `none`. В `GET /deal` — `lapse` у самой оферты и у прежних трат каждого векселя, `witnessed` у засчитанного ответа, `from_future` у оферты и у ответа — датированы позже, чем доказуемо существовали (blockchain.md §9.4); в следе цепи — `future_blocks`. Со-подписи слияний — склад `/cosigs` рядом с блоками (blockchain.md §6.4). Залог (records.md §9.8 v9): выкуп из него ответа не ждёт, трата до срока и до выкупа не обеспечена. В следе цепи (`GET /economy/footprint/<цепь>`) — попытки платить бумагой, которой не было (`unbacked_deals`, `unbacked_units`), ложные сторно (`false_reversals`) и держатели её бумаги с отрицательным остатком (`overdrawn`): раньше такой остаток молча пропускался, теперь его быть не должно, а если он есть — он виден.
- **Товарные нити (records.md §9.4 v4):** по каждой цепи — звенья труда, форки, битые звенья, пересечения часов (подписанные доказательства) и ещё не подтверждённый труд по предложенным осям: `GET /thread/<цепь>`.
- **Доли в общей вещи (ИР-013, решение участника 2026-10-06):** кому сколько **ресурса** вещи принадлежит — `GET /resource/<цепь>/<хеш>`: весь ресурс записи, сколько продано вперёд машино-часами и кому, сколько каждый дольщик уже истратил и сколько у него осталось, сколько истратил сам держатель, сколько отпущено и не оплачено, сколько свободно. Доля — не дробь, а **купленная порция ресурса**, поэтому витрина складывается из обычных записей (продажа машино-часов, покупка, расход купленного) и новых сущностей не требует. Отдельно показан перебор: ресурсом распорядились больше, чем его есть (`over_used`) — держатель работает на том, что уже продано; протокол этому физически не помешает, но числом это видно.
- **Склад (records.md §9.8 v4):** что цепь купила и может перепродать — `GET /stock/<цепь>`: покупки с партиями, сколько перепродано, списано, ждёт оплаты и в запасе, и по какой цене; в `GET /work/<цепь>/<хеш>` — и отпуски держателей этой вещи, и сделки с их источником (`source`), и заранее подписанные возвраты её покупок (`buybacks`, records.md §9.8 v5).
- **Партии (records.md §9.8 v2, records.md §9.9):** по каждому выходу — сколько продано, ждёт оплаты, списано и осталось, звенья, которые не сходятся (`records::check_lot`), — в `GET /thread/<цепь>` и `GET /work/<цепь>/<хеш>`; там же — какие отпуски взяты. Цены дня производства — опубликованный агрегат того дня: `GET /economy/rates?date=TS`.
- **Профили и потребности (records.md §8.6):** сканирует `Concept`-ы с фасетными тегами `kind:*`, группирует по цепям и отдаёт JSON-экспорт (`GET /profiles`, `GET /profiles/<chain>`) — навыки, потребности, желания, отрасли участников. Предназначен для ручной стыковки «потребность↔навык» или для передачи внешнему ИИ (проект LLM в себя не встраивает). Как и всё у агрегатора — производная, перепроверяемая по цепям.

**Агрегаторы — кэш и индекс, не источник истины.** Любое утверждение агрегатора может быть проверено P2P-обращением к исходной цепочке.

**Масштаб агрегации:**

| Уровень | Хранит |
|---------|--------|
| Минимальный | только свою цепочку |
| Локальный | цепочки известных пользователей |
| Полный | все публичные цепочки сети |

## 14. Открытые вопросы

### 14.1. Идентификация «последней» реакции
Агрегатор учитывает только последнюю `Reaction` пользователя на конкретный `target`. Рекомендуется использовать порядковый индекс блока в ветке (монотонный, не зависит от честности автора), а не `timestamp_claimed`.

### 14.2. Весовая функция реакций
Все пользователи имеют равный вес в реакциях? Или вес реакции масштабируется по накопленным трудочасам автора? Требует явного решения — влияет на расчёт агрегаторов.

### 14.3. Порядок элементов в Composite
Порядок ссылок в `Composite.parts` влияет на хеш. Варианты: сортировать (детерминированный хеш независимо от автора) или сохранять авторский порядок (семантически значимый, но непредсказуемый хеш). Выбор влияет на дедупликацию.

### 14.4. Верификация квалификации — РЕШЕНО (2026-09-11): принятая работа по осям
**Квалификация — это принятая другими работа, прочитанная по осям (ИР-022 шаг 11).** Разряда и лестницы разрядов больше нет (records.md §9.2): каждая приёмка уже говорит, чем была работа, разбивкой цены по осям (records.md §9.5 v4). Витрина показывает по работнику и по каждой оси, сколько **разных** цепей приняли такую работу и сколько часов: «по оси "работа под напряжением" приняли 5 цепей, 112 ч». Считаются разные принявшие цепи, а не приёмки; собственная цепь не свидетель — это само-поручительство бесплатно; работа обязана лежать в той цепи, которую называет ссылка приёмки; разбивка, не сходящаяся с ценой, ничего не заверяет. Заявление о себе (`grade:` в профиле) остаётся вольным текстом и показывается рядом — читатель сравнивает и решает, глобальный балл не вычисляется (принципы ИР-009/ИР-010). Заверение от нарисованных цепей остаётся возможным — ответ на это не счётчик, а поток доверия (ИР-009).

Было (2026-07-10 → 2026-09-11): лестница разрядов — обучение → экзамен (приёмка цепями с этим или высшим разрядом) → заверенный объём → следующий разряд; пилотная механика считала принявшие цепи по паре (специальность, разряд).

### 14.5. Пересчёт суточного агрегата — РЕШЕНО
Действует последняя запись на данную дату от данного агрегатора (закреплено в records.md §11.2).

### 14.6. Граница между PayloadRecord и пустым Concept — РЕШЕНО (2026-07-13)
Профиль и потребности выражаются `Concept`-ами с зарезервированными тегами (records.md §8.6), выбор записи — из универсальных каталогов (records.md §8.7). `Entity`/`Property` остаются для структурного описания сущностей, где важны типизированные атрибуты; свободное самоописание участника — теговый `Concept`.

### 14.7. Заявка на исполнение работы — РЕШЕНО (2026-07-15, ИР-006)
Без нового типа: заявка — `ConceptLink{kind:"берусь", from: свой навык, to: потребность}` (records.md §8.6), выбор исполнителя — существующее поле `executor` у `Pledge`. Под одну потребность может быть много «берусь»; наняли того, на кого указал `executor` (или с кем просто начали работать — обещание необязательно). Выбор по-прежнему социальный, но намерение теперь записано и видно в `DealView`.

### 14.8. Дополнительные измерения труда — РЕШЕНО
Отдельные **деятельности** со своими ставками, не надбавки и не поля (пример из `main_ideas.pdf`: «подготовка к операции» 3 стч/ч и «операция» 14 стч/ч — один хирург, разные деятельности). «Монтаж» и «монтаж на высоте» — разные специальности в статистике records.md §11.2. **С ИР-022 шаг 11** — разные **оси** разбивки: «монтаж на высоте» — ось со своей ценой (records.md §11.2), а не отдельная специальность. Принцип records.md §12.8 не тронут.
