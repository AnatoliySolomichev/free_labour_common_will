# Расширение браузера: окно соцслоя на любой странице (ИР-026, ИР-008)

**Статус:** черновик v0.3 (2026-10-24).
**Назначение:** интерфейс трёх сценариев ИР-026 — соцслоя (social.md), соревнований (contests.md) и отзывов о продукции (reviews.md) — прямо в браузере: человек смотрит ролик или товар и тут же видит картину своего круга, ставит лайк, пишет комментарий или отзыв. Нумерация разделов — своя (CLAUDE.md).

---

## 1. Назначение

Кнопка расширения на панели браузера открывает окно для **текущей страницы**: её ключ (social.md §3), картину круга — реакции, просмотры, комментарии, а у товара и отзывы (social.md §6, reviews.md §5) — и действия: 👍, 👎, снять, «смотрел», комментарий, отзыв со звёздами.

Ограничение ИР-008 соблюдено: **ключ остаётся у человека, подпись — его акт.** Расширение ничего не подписывает само: оно просит `bc` на том же компьютере, через механизм браузера native messaging (extension.md §3). Логика картины — одна, в C++: окно показывает то, что считает `bc social show` и `bc review show`, в машинном виде (`--json`).

## 2. Ключ: ветка браузера

Решение участника 2026-10-23: **сейчас — отдельная ветка браузера в `bc`, потом — свой ключ в самом браузере.**

- Заметки из окна подписывает `bc`, но не основной веткой, а **веткой браузера** — соседним с основным листом `0x80000000` (основной — `0x7FFFFFFF`), со своим ключом. У них общий родитель; он и отзывает ветку браузера (blockchain.md §6.7), не трогая основную, где труд и сделки.
- Заметки — односторонние записи: после момента компрометации они теряют вес (blockchain.md §6.7). Так что худшее, что может сделать захваченное расширение, — насорить заметками в ветке, которую отзовут.
- **Потом — свой ключ в браузере:** расширение само заводит ключ (неизвлекаемый Ed25519 WebCrypto), `bc` один раз заверяет его узлом дерева, дальше `bc` на компьютере не нужен. Это путь к телефонам: native messaging там нет. Цена — вторая реализация блоков и записей на JS, байт в байт как в C++, и картины — extension.md §7.

## 3. Хост native messaging

Браузер запускает `bc native-host` сам — через скрипт, который пишет `bc native-install` (extension.md §5) — и обменивается с ним кадрами: 4 байта длины (порядок байтов машины) и JSON. Один процесс отвечает на любое число запросов, пока браузер не закроет канал. Окно держит один канал, пока открыто (`runtime.connectNative`): `bc` запускается один раз на открытие окна, а не на каждый запрос — это важно, когда `bc` в контейнере и каждый запуск идёт через `docker exec` (extension.md §5.1).

Запрос: `{"id": 1, "cmd": "…", …}`. Ответ: `{"id": 1, "ok": true, "data": {…}}` для чтения, `{"id": 1, "ok": …, "text": "…", "error": "…"}` для записи.

**Белый список** — как у черновика писаря (records.md §8.8): расширению доступны только заметки и чтение картин.

| `cmd` | Поля | Что делает |
|---|---|---|
| `whoami` | — | своя цепь, агрегатор, ветка браузера |
| `key` | `subject` — ссылка | ключ страницы (social.md §3) |
| `show` | `subject`, `hops`, `all` | картина: `bc social show --json` |
| `reviews` | `subject`, `hops`, `all` | картина товара: `bc review show --json` |
| `like`, `dislike`, `unlike` | `subject` | реакция (social.md §4) |
| `comment` | `subject`, `text`, `re` | комментарий или ответ |
| `retract` | `subject` — свой комментарий | снять его |
| `follow`, `unfollow` | `subject` — цепь | подписка |
| `watch` | `subject`, `from`, `to`, `speed`, `now` | просмотр: в журнал или сразу (social.md §4.1) |
| `views.publish` | — | журнал — суточным пакетом |
| `review` | `subject`, `stars`, `text` | отзыв (reviews.md §2) |
| `same` | `subject`, `other`, `no` | «тот же товар» / «не тот же» (reviews.md §3) |

Всё прочее — отказ «этого расширению нельзя»: ни переводов, ни приёмок, ни операций с ключами отсюда не сделать (градиент необратимости, ИР-002). Текст, начинающийся с «--», отвергается: его приняли бы за флаг.

Хост — сам `bc`: команда выполняется в том же процессе, всё, что она печатает, уходит в ответ, а stdout занят кадрами протокола.

Аргументы, с которыми браузер запускает хост, `bc` не читает: Chromium передаёт происхождение расширения (`chrome-extension://…/`), Firefox — путь к манифесту хоста и идентификатор расширения. Какому расширению можно подключаться, решает манифест хоста (extension.md §5).

## 4. Окно

- **Ключ страницы** и чья подпись — «вы: … · подпись — ветка браузера».
- **Отзывы круга** — у ключей товара (`gtin:`, `model:`, `ozon:`, `wb:`, `ymarket:`, `amazon:`, `ali:`): число, медиана, раскладка, каждый отзыв с пометкой о покупке и «полезно»; форма отзыва со звёздами.
- **Реакции и просмотры круга**, кнопки 👍, 👎, «снять», «смотрел» (в журнал; «опубликовать журнал» — внизу).
- **Комментарии круга** — деревом ответов; форма комментария.

Чужие тексты — комментарии, отзывы — вставляются только как текст (`textContent`), никогда как разметка: они приходят из чужих цепей. Окно работает под политикой безопасности расширения по умолчанию — без `eval` и встроенных скриптов.

## 5. Установка

1. Собрать `bc` и завести личность (`bc identity create`), если её нет.
2. Поставить хост:
   ```
   bc native-install --via URL_АГРЕГАТОРА [--browser chromium|chrome|firefox|all]
   ```
   Команда заводит ветку браузера, пишет скрипт запуска `native-host.sh` рядом с данными и манифест хоста `org.free_labour.bc.json` в каталог браузера: `~/.config/chromium/NativeMessagingHosts/`, `~/.config/google-chrome/NativeMessagingHosts/`, `~/.mozilla/native-messaging-hosts/`. `--profile КАТАЛОГ` — в свой профиль Chromium или Chrome (так делают проверки). У Firefox такого каталога в профиле нет: манифест хоста он ищет только в `~/.mozilla/native-messaging-hosts/` — и в новых версиях, что держат профили в `~/.config` по XDG. Поэтому `--profile` с `--browser firefox` — отказ.
3. Загрузить расширение:
   - **Chrome, Chromium** — `chrome://extensions` → «Режим разработчика» → «Загрузить распакованное» → каталог `modules/extension`.
   - **Firefox ESR** (в Debian — пакет `firefox-esr`), а также Developer Edition и Nightly — насовсем, пакетом `build/modules/extension/bc.xpi`; его собирает `cmake --build build`. Пакет не подписан Mozilla, а эти сборки умеют не требовать подписи:
     1. `about:config` → `xpinstall.signatures.required` → `false`;
     2. `about:addons` → ⚙ → «Установить дополнение из файла…» → `bc.xpi`;
     3. кнопка расширения появится в меню расширений (значок пазла) — её можно закрепить на панели.

     После обновления окна — пересобрать и поставить `bc.xpi` тем же путём: поверх ставится и та же версия.
   - **Обычный Firefox** (выпуски и беты) — без подписи Mozilla только временно, до перезапуска: `about:debugging` → «Этот Firefox» → «Загрузить временное дополнение» → `modules/extension/manifest.json`. Подписи пока нет (extension.md §7).

Идентификатор расширения в Chrome постоянный — его задаёт открытый ключ в `manifest.json`: `dmmadjknblhkhcfhjblkaikanclebljf`; только ему манифест хоста разрешает подключаться. В Firefox — `bc@free-labour.org`.

Если окно пишет «хост bc не установлен» — нет манифеста в каталоге браузера. «Хост bc не запускается» (Firefox) — нет скрипта запуска, на который указывает манифест, или он не исполняемый. «bc завершился, не ответив» — скрипт запуска не смог поднять `bc`. Chromium и Firefox сообщают об этом разными словами; окно переводит и те, и другие. Firefox «хоста нет» и «хост не пускает это расширение» не различает — окно так и пишет: «не установлен или не пускает».

### 5.1. Браузер на хосте, bc в контейнере

Так устроена разработка: `bc` собран и живёт в контейнере, а браузер — на хосте. Хост браузер запускает у себя, на хосте, — значит, скрипт запуска должен звать `bc` через `docker exec`. Пути хоста (`$HOME`) из контейнера не видны, поэтому `bc native-install --docker КОНТЕЙНЕР` ничего не ставит, а печатает **сценарий для хоста**:

```
# в контейнере, в каталоге проекта (он виден и с хоста):
build/modules/cli/bc native-install --via URL_АГРЕГАТОРА --docker КОНТЕЙНЕР > build/install-host.sh
# на хосте, в том же каталоге:
sh build/install-host.sh
```

Или одной строкой на хосте:

```
docker exec КОНТЕЙНЕР /workspace/build/modules/cli/bc native-install --via URL_АГРЕГАТОРА --docker КОНТЕЙНЕР | sh
```

Ветку браузера команда заводит сразу, в контейнере. Сценарий пишет скрипт запуска `~/.local/share/bc/native-host.sh` — `exec docker exec -i КОНТЕЙНЕР …/bc --data-dir … native-host --via …` — и манифесты в каталоги браузеров хоста (`--browser`, как в extension.md §5). Потом проверяет установку: шлёт `bc` кадр `whoami` тем же путём, каким пойдёт браузер.

- **`КОНТЕЙНЕР`** — имя из `docker ps` на хосте. Имя надёжнее идентификатора: при пересборке VS Code заводит новый контейнер с тем же именем, а идентификатор (`hostname` в контейнере) меняется.
- **`URL_АГРЕГАТОРА`** — каким агрегатор видно **из контейнера**: `bc` работает там.
- **docker без `sudo`** (группа `docker`): хост браузер запускает от вашего имени. `DOCKER_HOST` на момент установки сценарий переносит в скрипт запуска — у браузера, запущенного с рабочего стола, своего окружения оболочки нет.
- **Браузер не из песочницы:** Chromium из Snap и браузеры из Flatpak не дают хосту запускать программы вне песочницы, `docker` в том числе. Подходят браузеры из пакетов `.deb`: `chromium` и `firefox-esr` в Debian, Google Chrome.
- **Данные `bc`** (`~/.blockchain` в контейнере) пересборка контейнера сотрёт. Ключ личности держите на томе или в каталоге хоста вне репозитория (`--data-dir`) — и с тем же `--data-dir` ставьте хост.

## 6. Проверка

`modules/extension/tests/host-e2e.sh` (в `ctest` — `e2e_extension`): свой агрегатор, личность, `bc native-install` в отдельный профиль Chromium (и отказ `--profile` для Firefox), затем

- **протокол хоста** (`host_test.py`): кадры, чтение картин, запись заметок в ветку браузера, отказ переводу и битому JSON;
- **сценарий для хоста** (extension.md §5.1): `bc native-install --docker` → `install-host.sh` с подменённым `docker` и своим домом «хоста» → манифесты всех браузеров и тот же `host_test.py`, но хост запускается, как его запускает Firefox на хосте участника, — скриптом из манифеста, с аргументами Firefox;
- **настоящий Chromium** (`browser_test.cjs`, Playwright, окно под `xvfb-run`): окно на странице ролика и товара, лайк, комментарий, отзыв; чужая разметка в комментарии остаётся текстом; слова окна, когда манифеста нет, он для чужого расширения или `bc` вышел, не ответив. Без Node.js и Playwright эта часть пропускается;
- **настоящий Firefox ESR** (`firefox_test.py`, geckodriver, `-headless`): `bc.xpi` ставится насовсем без подписи, как у участника (extension.md §5); то же окно, что в Chromium, и те же слова об ошибках хоста, плюс «нет скрипта запуска». Манифест хоста Firefox ищет только в `~/.mozilla`, поэтому geckodriver и Firefox в проверке живут со своим `HOME`. geckodriver запускается с `--allow-system-access`, иначе он не открывает страницы расширения. Без Firefox и geckodriver эта часть пропускается.

Node.js, Playwright, Firefox ESR и geckodriver — в образе (`docker/Dockerfile`).

## 7. Чего нет

- **Своего ключа в браузере** (extension.md §2) — следующий шаг, к телефонам.
- **Панели прямо на странице** — кнопок под роликом: пока окно по кнопке расширения.
- **Соревнований в окне:** попытке нужен хеш видеофайла, это `bc contest attempt`.
- **Магазинов расширений и подписи Mozilla.** В Chromium расширение — «распакованное», для разработчиков. В Firefox — неподписанный `bc.xpi`, а его насовсем ставят только ESR, Developer Edition и Nightly. Обычному Firefox нужна подпись на addons.mozilla.org: это аккаунт участника и отдельный шаг публикации.

## 8. Открытые вопросы

Решено при реализации — на пересмотр участнику:

1. Окно по кнопке расширения, а не панель на странице (extension.md §7).
2. Ветка браузера — лист `0x80000000`, сосед основного (extension.md §2).
3. «Смотрел» кладёт просмотр в журнал, а не сразу в цепь; журнал публикуется кнопкой (social.md §4.1).
4. У товара отзывы показаны выше комментариев.
5. Браузер на хосте, `bc` в контейнере — `bc native-install --docker` печатает сценарий для хоста, а не ставит файлы: пути хоста видны только там (extension.md §5.1).

Открыто:

6. Свой ключ в браузере: как `bc` заверяет узел с чужим открытым ключом, где хранить состояние ветки в браузере.
7. Нужна ли окну картина со вторым шагом круга (`--hops 2`) — сейчас только шаг 1.

Решено при поддержке Firefox (v0.3) — на пересмотр участнику:

8. В Firefox — постоянная установка неподписанного `bc.xpi`: в ESR, Developer Edition и Nightly это разрешает `xpinstall.signatures.required = false`. Подпись Mozilla для обычного Firefox — не сейчас (extension.md §7). `bc.xpi` собирает CMake вместе с `bc`, и проверка ставит тот же файл, что участник.

## 9. История изменений

- **v0.3** (2026-10-24) — Firefox (у участника на хосте Firefox ESR 153, Chromium нет): окно проверено в настоящем Firefox ESR той же версии — `firefox_test.py` в `e2e_extension`, Firefox и geckodriver в `docker/Dockerfile`. `bc.xpi` для постоянной установки (extension.md §5). Слова Firefox об ошибках хоста окно переводит, как и слова Chromium; проверки обоих браузеров смотрят эти слова. `--profile` с `--browser firefox` — отказ: манифест хоста Firefox ищет только в `~/.mozilla`. Сценарий для хоста в проверке ставит манифесты всех браузеров и запускает хост с аргументами Firefox.
- **v0.2** (2026-10-23) — браузер на хосте, `bc` в контейнере (extension.md §5.1): `bc native-install --docker КОНТЕЙНЕР` печатает сценарий для хоста — скрипт запуска через `docker exec`, манифесты, проверка кадром `whoami`. Окно держит один канал к `bc` (`connectNative`) вместо запуска на каждый запрос; слова браузера об ошибках хоста — по-человечески. Проверка `e2e_extension` прогоняет и сценарий для хоста.
- **v0.1** (2026-10-23) — окно расширения для соцслоя и отзывов (решения участника 2026-10-23): подпись — `bc` веткой браузера через native messaging, белый список заметок; `bc native-host`, `bc native-install`; `--json` у `bc social show` и `bc review show`; проверка протокола и настоящего Chromium (`e2e_extension`); Node.js и Playwright — в `docker/Dockerfile`.
